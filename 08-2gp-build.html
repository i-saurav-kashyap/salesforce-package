Part 8

Build the Same App as a 2GP

The same application, as a 2GP managed package, from an empty repo to a released version a customer can install. Every command lists: why you run it, which org it talks to, what authentication it uses, what API is behind it, what changes locally, and what changes in Salesforce.

GitHub → DX project → sfdx-project.json → namespace → Dev Hub → scratch org
   → develop → test → sf package create → sf package version create (beta)
   → install into a clean org → fix → new version → promote (released) → install → upgrade

Step 1 — Repo and project

bash
cd sample-project
git init
git add -A && git commit -m "feat: ops toolkit core + field ops"
gh repo create ops-toolkit --private --source=. --push     # or create it in the GitHub UI
WhyIn 2GP the repo is the package. Doing this first is not ceremony.
Org involvedNone.
Changes locally.git/, a remote.
Changes in SalesforceNothing.

Step 2 — Authenticate the Dev Hub and register/link the namespace

bash
sf org login web --alias devhub --set-default-dev-hub
sf org login web --alias nsorg                # the DE org that owns the namespace
sf org list --all

In nsorg: register the namespace (Setup → Package Manager → Developer Settings → Edit). In devhub: App Launcher → Namespace Registries → Link Namespace → authenticate as the nsorg admin.

WhyThe Dev Hub must be allowed to stamp your namespace onto package versions.
Auth usedInteractive OAuth in both cases; the link stores a trust relationship in the Dev Hub.
VerifyNamespace Registries list shows the namespace; sfdx-project.json's namespace matches it exactly.
Common errorThe namespace 'opskit' is not linked to this Dev Hub — you either linked a different org or typo'd the namespace in the project file.

Step 3 — Develop in a scratch org

bash
./scripts/create-dev-org.sh dev1 7
# equivalently, by hand:
sf org create scratch -f config/project-scratch-def.json -a dev1 -d 7 --set-default
sf project deploy start --target-org dev1
sf org assign permset --name Ops_Core_User --name Ops_Field_Ops_User --target-org dev1
sf apex run test --target-org dev1 --code-coverage --result-format human
Which orgRequest goes to the Dev Hub; the resulting org is a new scratch org.
Salesforce APIThe CLI inserts a ScratchOrgInfo record (Tooling/SOAP) in the Dev Hub; org provisioning does the rest; then a Metadata API deploy for your source.
Namespaced?Yes — because sfdx-project.json has a namespace. Your components appear as opskit__…, exactly as a customer will see them.
VerifyTests green, app usable, sf org open works.

Step 4 — Create the package definitions (once per package, ever)

bash
sf package create \
  --name "Ops Toolkit Core" \
  --package-type Managed \
  --path packages/core \
  --description "Core objects and services for Ops Toolkit" \
  --target-dev-hub devhub

sf package create \
  --name "Ops Toolkit Field Ops" \
  --package-type Managed \
  --path packages/field-ops \
  --description "Field operations console" \
  --target-dev-hub devhub

sf package list --target-dev-hub devhub --verbose
git diff sfdx-project.json      # look at what the CLI wrote
WhyRegisters the package identity with Salesforce. Done once; not per version.
Which orgDev Hub.
APITooling API — inserts a Package2 record.
CreatesA 0Ho package ID.
Changes locallypackageAliases gains "Ops Toolkit Core": "0Ho...". Commit this.
Common errorsNamespace not linked (Step 2 incomplete); 2GP not enabled (Dev Hub setting); Package name already in use in this Dev Hub.

Step 5 — Create a BETA version of Core

bash
sf package version create \
  --package "Ops Toolkit Core" \
  --installation-key "LearnPackaging123" \
  --code-coverage \
  --wait 30 \
  --target-dev-hub devhub
WhyTurn source into an installable artifact.
Which orgDev Hub — but the actual build happens in a Salesforce-managed environment (see Part 18).
APITooling API — inserts a Package2VersionCreateRequest (08c) and polls it.
What Salesforce doesReads your packages/core source, spins up a build org, installs declared dependencies, deploys the metadata, compiles Apex, runs your tests (because of --code-coverage), records coverage, and mints a Package2Version (05i) with a SubscriberPackageVersionId (04t).
Changes locallypackageAliases gains "Ops Toolkit Core@1.0.0-1": "04t...".
Expect to seeA Successfully created the package version message with the 04t and a ready-to-paste install URL.
DurationMinutes, not seconds. 5–20 is normal; it is building an org.

If it fails, do not guess — read the request:

bash
sf package version create list --target-dev-hub devhub          # recent attempts + status
sf package version create report --package-create-request-id 08c... --target-dev-hub devhub

Step 6 — Create a BETA version of Field Ops (the dependent package)

bash
sf package version create \
  --package "Ops Toolkit Field Ops" \
  --installation-key "LearnPackaging123" \
  --code-coverage --wait 40 --target-dev-hub devhub

The declared dependency {"package":"Ops Toolkit Core","versionNumber":"1.0.0.LATEST"} makes Salesforce install Core's latest 1.0.0 build into the build environment before compiling Field Ops. That is why ServiceRequestConsoleController can reference ServiceRequestService and still compile. Remove the dependency and this step fails with a compile error — try it once on purpose (drill 8).

Step 7 — Install into a customer-like org

bash
./scripts/create-install-test-org.sh 04t...CORE LearnPackaging123
# then the dependent package into the SAME org:
sf package install --package 04t...FIELDOPS --installation-key "LearnPackaging123" \
  --target-org customer1 --wait 20 --publish-wait 20 --no-prompt

sf package installed list --target-org customer1
Which orgThe clean, non-namespaced scratch org.
APITooling API PackageInstallRequest; the CLI polls until Success.
Order mattersCore first. Installing Field Ops into an org without Core fails with a missing-dependency error naming the required 04t.
VerifyAssign both permission sets to a non-admin user and use the app. Confirm namespace prefixes, the CMDT default row, the LWC on an app page, and that Apex is not editable.

Step 8 — Promote to Released

bash
sf package version promote --package "Ops Toolkit Core@1.0.0-1" --target-dev-hub devhub
sf package version promote --package "Ops Toolkit Field Ops@1.0.0-1" --target-dev-hub devhub
sf package version list --released --target-dev-hub devhub
WhyOnly released versions can be installed in production, listed on AppExchange, or used as an ancestor.
Requirement≥75% Apex code coverage recorded at version-create time. If you created the version without --code-coverage, promotion fails and you must build a new version.
IrreversibleYes. There is no demote.
Tag itgit tag -a core-v1.0.0 -m "Ops Toolkit Core 1.0.0 (04t...)" && git push --tags

Step 9 — Ship 1.1 with ancestry, and upgrade a customer

Edit sfdx-project.json:

json
{
  "path": "packages/core",
  "package": "Ops Toolkit Core",
  "versionName": "Summer Release",
  "versionNumber": "1.1.0.NEXT",
  "ancestorVersion": "1.0.0.1",
  "default": true
}
bash
# add something additive first (a new field + a new global method), then:
sf package version create --package "Ops Toolkit Core" \
  --installation-key "LearnPackaging123" --code-coverage --wait 30
sf package version promote --package "Ops Toolkit Core@1.1.0-1"

# upgrade the customer org that already has 1.0
sf package install --package 04t...CORE_1_1 --installation-key "LearnPackaging123" \
  --target-org customer1 --wait 20 --no-prompt
sf package installed list --target-org customer1

Verify the whole point: records created under 1.0 still exist with their data; the new field is present and empty; the customer never re-entered anything.

Command reference for this page

CommandTalks toCreates / changes
sf package createDev HubPackage2 (0Ho) + alias in sfdx-project.json
sf package version createDev Hub → build service08c request → 05i version → 04t + alias
sf package version create reportDev HubNothing — reads the request, including the error
sf package version listDev HubNothing — lists versions, coverage, released flag
sf package version promoteDev HubFlips IsReleased — permanent
sf package installTarget orgPackageInstallRequest in that org
sf package installed listTarget orgNothing — shows installed versions
sf package version reportDev HubNothing — details of one version incl. dependencies

Verification gate

  • Two packages exist in sf package list with 0Ho IDs
  • Both have at least one version with a 04t, and packageAliases is committed
  • Both installed into a clean non-namespaced org, in dependency order
  • A non-admin user with only your permission sets can use the app
  • Both versions promoted; sf package version list --released shows them
  • A 1.1 built with ancestorVersion, installed as an upgrade, data preserved
  • Git tags exist for each released version
