Authentication in CI — JWT, not passwords

Interactive OAuth cannot work in a runner. The supported answer is the JWT bearer flow: a Connected App in the Dev Hub trusts a certificate you hold.

  1. Generate a key pair (keep server.key out of Git, forever): [[code bash]] openssl req -x509 -sha256 -nodes -days 3650 -newkey rsa:2048 \ -keyout server.key -out server.crt \ -subj "/CN=OpsToolkitCI" [[/code]]
  2. Create a Connected App in the Dev Hub: Setup → App Manager → New Connected App. Enable OAuth, callback URL http://localhost:1717/OauthRedirect, scopes api, refresh_token offline_access, Use digital signatures → upload server.crt. Save the Consumer Key.
  3. Pre-authorise your user: Manage → Edit Policies → Permitted Users = Admin approved users are pre-authorized, then assign a profile/permission set that includes your CI user.
  4. Test it locally before trusting CI: [[code bash]] sf org login jwt --client-id \ --jwt-key-file server.key --username ci-user@example.com \ --set-default-dev-hub --alias devhub [[/code]]
  5. Store secrets in GitHub → Settings → Secrets and variables → Actions: DEVHUB_CLIENT_ID, DEVHUB_USERNAME, DEVHUB_JWT_KEY (the whole PEM), PACKAGE_INSTALL_KEY.

Secret hygiene, non-negotiable: the private key never enters the repo; the workflow writes it to a file and deletes it in the same step; secrets are never echoed; use environment protection rules so only the release workflow can read release secrets. A leaked Dev Hub key means someone else can publish package versions under your identity.

Workflow 2 — build, install-test, promote

[[file sample-project/.github/workflows/package-release.yml yaml]]

The install-test step is the point of this workflow. Creating a version proves it compiles. Installing it into a clean non-namespaced org and running the tests there proves it works the way a customer will experience it. Skipping that step is how “it built fine” becomes a support escalation.

Design choices worth copying

  • Promotion is manual and explicit (workflow_dispatch input, or a protected environment requiring approval). Promotion is irreversible — it should never happen by accident on a merge.
  • Beta on every merge, release on a tag. Betas are cheap; use them constantly.
  • The workflow commits sfdx-project.json so the new 04t aliases are recorded in Git. Without this, the repo forgets which commit became which version.
  • Every org is deleted in an always() step. Leaked scratch orgs exhaust your limits and then block everyone.
  • Version numbers are bumped in a PR, not by CI. Deciding “this is 1.1 not 1.0.1” is a human decision about compatibility.

Tag every promoted version: git tag -a core-v1.1.0 -m "04t...". The tag message containing the 04t has saved more incidents than any dashboard.

What to add next (in order of value)

  1. Jest tests for LWC (npm run test:unit) in the PR job — fast and catches real bugs.
  2. Prettier + ESLint as a pre-commit hook, so formatting never appears in review diffs.
  3. An upgrade-test job: create an org, install the previous released version, seed data, install the new version, assert the data survived. This is the highest-value job in an ISV pipeline and almost nobody has it.
  4. Scheduled dependency check: nightly job that reports if a dependency has a newer released version.
  5. Release notes generation from the commit range between tags.

Verification

  • JWT login works locally with the same key CI will use
  • A PR triggers validation and it goes green
  • A deliberately failing test blocks the PR
  • The release workflow produces a 04t and installs it into a clean org
  • Scratch orgs are always deleted, even when the job fails
  • Promotion requires a human action
  • The repo contains the alias for every version you have built
