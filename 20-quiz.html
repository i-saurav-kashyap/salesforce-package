Part 20

Architect-Level Interview

The exam. Answer out loud or in writing before opening any solution — a recognised answer is not a known answer. Bring your answers to me and I will grade them the way a senior Salesforce architect would in an interview: I will push on the weak parts rather than accept the shape of a correct answer.

How to use this page. Work a tier at a time. Say the answer, then open the “what a strong answer contains” block and score yourself: 3 = I said all of that, 2 = I said the core, 1 = I recognised it, 0 = no. Anything below 2 goes back to the linked page.

Tier 1 — Foundations

Q1. What is a scratch org?

What a strong answer contains

Disposable, source-driven org created by a Dev Hub from a JSON definition (edition, features, settings, namespace), living 1–30 days, with source tracking. Its state is never authoritative — Git is. A weak answer says “a temporary developer org” and stops. A strong one mentions the Dev Hub, the definition file, source tracking, and the fact that losing one should cost nothing. (Part 9)

Q2. What is a namespace, and what does registering one commit you to?

Strong answer

A globally-unique prefix applied to every packaged component, giving collision avoidance, isolation and identity. Registered in exactly one DE org, permanently: it cannot be renamed, moved, released or reused. In 1GP that org becomes the packaging org; in 2GP it is linked to the Dev Hub as a Namespace Registry. (Part 1)

Q3. Name the four IDs and what each identifies.

Strong answer

033 = 1GP package. 0Ho = 2GP package definition. 08c = a version-create request (attempt). 05i = the version record in your Dev Hub. 04t = the subscriber package version — the only one a customer or a dependency ever needs.

Tier 2 — Structural understanding

Q4. Why does 2GP not need a packaging org?

Strong answer

Because the input to a version build is your source tree, not an org's state. The Dev Hub holds package identity (Package2) and version records, and Salesforce provisions a throwaway build environment to compile each version. There is nothing left for a permanent packaging org to hold. Follow-ups a strong candidate handles: what the Dev Hub does hold; what happens if the Dev Hub is lost (you cannot build new versions; existing installs keep working); why 1GP must have one.

Q5. How does package ancestry work, and why does 1GP not need it?

Strong answer

Ancestry is the declared lineage (ancestorVersion/ancestorId) stating which released version a new version descends from. It enables upgrades and lets Salesforce enforce compatibility at build time (e.g. refusing a build that removed a released global method). 1GP does not need it because the packaging org has exactly one state, so version N+1 implicitly follows version N — which is also why 1GP cannot branch. Bonus: without ancestry your customers can only uninstall/reinstall, losing data.

Q6. How does a 2GP dependency resolve — at build time and at install time?

Strong answer

Build: the declaration in sfdx-project.json resolves to a concrete 04t (LATEST resolves to the newest matching build; an alias or ID pins it). Salesforce installs the dependency into the build environment before deploying and compiling your source — which is why a missing declaration shows up as an Apex compile error. The resolved dependency list is recorded on the version. Install: Salesforce checks that list against the target org and fails, naming the required 04t, if it is absent. Dependencies are never auto-installed.

Q7. Why use a non-namespaced scratch org for customer-like testing?

Strong answer

A real subscriber org has no namespace of its own; your package's components arrive prefixed while the subscriber's stay unprefixed. A non-namespaced org with your package installed reproduces exactly that. A namespaced org makes locally-pushed components look packaged, hiding the difference between “works because I pushed it” and “works because it is in the package” — which is precisely the class of bug (missing components, permission gaps, hard-coded API names) that install testing exists to catch.

Q8. What can and cannot change after a managed version is released?

Strong answer

Can: add components, add global methods, change public internals freely, add picklist values, change labels, deprecate. Cannot: remove/rename/change the signature of anything global, reduce its visibility, delete released objects/fields, change field types, change the namespace, delete or un-release a version. A strong answer adds: removing a component from the package does not remove it from subscriber orgs — it orphans it. (Part 5)

Tier 3 — Design

Q9. Design the org architecture for a 3-package AppExchange product.

What I will be listening for
  • Permanent: PBO (Publishing Console, Environment Hub, LMA) with the Dev Hub enabled in it; one namespace org (DE) linked as a Namespace Registry, never developed in.
  • Ephemeral: namespaced dev scratch orgs per developer; per-PR CI scratch orgs; non-namespaced install-test orgs; an upgrade-test org holding the previous released version.
  • Long-lived: QA org, UAT/demo org (listing screenshots), optional Trialforce source org.
  • Repo: monorepo with three package directories; dependencies declared; LATEST on feature branches, pinned on release branches; tags per released version; packageAliases committed.
  • Process: PR validation in a scratch org; beta on merge; install-test in a clean org; promotion behind a manual approval; documented install order; upgrade rehearsal with realistic data.
  • Risk answers: what if the Dev Hub is lost; what if the namespace org is deactivated; why one Dev Hub per company; why nobody develops in the namespace org.

Q10. Package B (2GP) must call Package A (1GP). Walk me through it.

Strong answer

Supported. Declare the dependency by subscriberPackageVersionId (a 04t) because a 1GP package has no Package2 record to alias. Use a released 1GP version (a beta could never be satisfied in production). At build, Salesforce installs that exact version into the build environment; at install, the customer must already have it. B can only call A's global surface. There is no LATEST for a 1GP dependency, so bumping it is a deliberate commit. The reverse — 1GP depending on 2GP — has no declaration mechanism at all. Flag honestly which details you would verify in current docs (installation keys for dependencies, shared-namespace rules).

Q11. Your customer's upgrade to 1.2 failed. Diagnose.

How to reason, not one answer
  1. Read the actual error — upgrade failures are usually explicit (validation rule, required field, Apex compile error, missing dependency).
  2. Data-driven? A newly-required field or new validation rule that their existing data violates. Most common. Fix: ship non-required, clean up, tighten later.
  3. Dependency? 1.2 requires a newer version of a dependency that they have not upgraded. Fix: upgrade the dependency first; document the order.
  4. Compilation? Your Apex compiles in the subscriber org's context — their metadata is part of that context. Something in their org (a deleted field your code references dynamically, a conflicting component) broke it.
  5. Post-install script? It hit a governor limit or assumed a starting state their org does not have.
  6. Reproduce in an org with 1.1 installed and data shaped like theirs. Then add that scenario to the upgrade-test job so it never recurs.

Q12. When would you argue against splitting into more packages?

Strong answer

When the packages always ship together and every customer gets all of them: you have added install steps, version-coordination overhead, dependency declarations, and more upgrade failure modes for no licensing or cadence benefit. Split when release cadence genuinely differs, when modules are sold separately, or when a stable core needs protecting from a volatile UI. A candidate who says “more packages = better modularity” has not run an upgrade for 200 customers.

The final question

In under three minutes, without notes: trace a single line of code from your laptop to a paying customer's org. Name every org, artefact, ID and gate it passes through, and say what would break at each step if you got it wrong.

When you can do that fluently, you have finished this course and can honestly say: “I built a Salesforce application from scratch, packaged it as a managed package in both generations, created package versions and dependencies, tested installation and upgrades, connected the solution to Partner Console, and understand how it becomes an AppExchange product.”
