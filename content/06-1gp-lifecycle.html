Now do it. Every step below states: what you do, what Salesforce does, which org is involved, what artifact appears, and how you verify it. Work top to bottom in one sitting if you can — the whole loop takes about two hours the first time.

Step 1 — Project

You:

[[code bash]] cd sample-project/1gp cat sfdx-project.json # note: NO "namespace" key, NO package definitions [[/code]]

Salesforce: nothing yet — this is purely local. Why no namespace key: in 1GP the packaging org applies the namespace on deploy. If you put "namespace": "opskit" here, the CLI would expect your local source to already be namespaced and you would get confusing mismatches. Verify: ls force-app/main/default shows classes, objects, labels, permissionsets, tabs.

Step 2 — Authenticate

[[code bash]] sf org login web --alias pkgorg sf org display --target-org pkgorg [[/code]]

Salesforce: OAuth web flow; the org issues a refresh token that the CLI stores locally. Artifact: ~/.sfdx/<username>.json. Verify: sf org list shows pkgorg as Connected.

Step 3 — The packaging org

You: decide which DE org this is (the one you reserved for the namespace) and never use it for anything else. Salesforce: nothing — “packaging org” is a role you assign, not a setting you flip. Verify: you can log in via sf org open --target-org pkgorg and Setup → Package Manager exists.

Step 4 — Register the namespace

You (UI, packaging org): Setup → Package Manager → Developer Settings → Edit → Continue → type namespace → Check Availability → Review → Save.

Salesforce: permanently associates the namespace with this org and starts prefixing every new custom component created in it. Artifact: the namespace prefix shown on the Package Manager page.

Verify:

[[code bash]] sf data query --target-org pkgorg \ --query "SELECT Id, NamespacePrefix FROM Organization" [[/code]]

The result must show your namespace. If it is blank, the registration did not save.

Point of no return #1. After this, every custom object and class created in this org carries the prefix, and the namespace can never be moved to another org.

Step 5 — Create the package

You (UI, packaging org): Package Manager → Packages → New:

  • Package Name: Ops Toolkit Core (1GP)
  • Description: what it is
  • Managed: ✔ (this checkbox is why the namespace had to come first)
  • Optionally a Post Install Script and Uninstall Script — leave blank for now

Salesforce: creates the package container. Artifact: a package with a 033 ID (visible in the URL of the package detail page).

Verify: sf package1 version list --target-org pkgorg runs without error (it will be empty), and the package appears under Packages.

Step 6 — Deploy metadata and add it to the package

[[code bash]] # from sample-project/1gp sf project deploy start --source-dir force-app --target-org pkgorg sf apex run test --target-org pkgorg --code-coverage --result-format human --wait 10 [[/code]]

Salesforce: Metadata API deploy → components created with your namespace prefix → Apex compiled. Verify: Setup → Object Manager shows Service Request with API name opskit__Service_Request__c, and tests pass at >75%.

You (UI): Package Manager → your package → Add Components. Add:

  • Custom Object: Service Request (fields, validation rule and list view come along)
  • Custom Metadata Type: Ops Setting — and separately the Custom Metadata record “Default”
  • Apex Classes: OpsSettings, ServiceRequestService, ServiceRequestSelector, ServiceRequestServiceTest
  • Custom Labels: the three Ops_* labels
  • Permission Set: Ops Toolkit Core User
  • Custom Tab: Service Requests

Verification that catches the #1 1GP mistake: after adding, the package detail page lists a component count. Compare it against find force-app -name '*-meta.xml' | wc -l mentally — not exact, but if the package shows 6 components and you deployed 20 files, you forgot something.

Step 7 — Upload a BETA version

You (UI): package detail → Upload. Version Name Beta 1, Version Number 1.0, Password (installation key) LearnPackaging123, and choose Managed — Beta.

Or CLI:

[[code bash]] sf package1 version create \ --target-org pkgorg \ --package-id 033xx0000004Cxx \ --name "Beta 1" --version "1.0" \ --installation-key "LearnPackaging123" --wait 20 [[/code]]

Salesforce (behind the scenes): creates a PackageUploadRequest; validates the component set; compiles all packaged Apex; runs your tests Inference (a released upload definitively runs them and enforces 75%); snapshots the components; mints a SubscriberPackageVersion (04t) and an install URL. It emails you when done.

Artifact: a row under Versions with a 04t ID and an install URL.

Verify:

[[code bash]] sf package1 version list --package-id 033xx0000004Cxx --target-org pkgorg [[/code]]

Step 8 — Install the beta in a clean org

[[code bash]] # A customer-like org: NOT namespaced, never saw your source. sf org create scratch --definition-file ../config/customer-like-scratch-def.json \ --alias customer1 --duration-days 2 --no-namespace --target-dev-hub devhub sf package install --package 04txx0000000001AAA \ --installation-key "LearnPackaging123" \ --target-org customer1 --wait 20 --publish-wait 20 --no-prompt sf package installed list --target-org customer1 [[/code]]

Beta versions may be installed in scratch orgs, sandboxes, DE orgs and Trialforce source orgs — not production. That is the practical difference between beta and released.

Verify like a customer, not like a developer:

  • Setup → Installed Packages shows your package, version 1.0, with your namespace
  • Create a user (or use yourself) without System Administrator, assign only opskit__Ops_Core_User, and confirm they can see the tab and create a request
  • Object Manager shows the fields prefixed opskit__
  • The Apex classes are visible but not editable — that is namespace isolation working
  • SELECT SLA_Days__c FROM opskit__Ops_Setting__mdt returns your shipped “Default” record

Step 9 — Find a defect on purpose

You will find one. Typical first-install defects, all real:

Step 10 — Fix and upload a new version

[[code bash]] # fix locally, commit, redeploy git commit -am "fix: grant tab visibility in Ops_Core_User" sf project deploy start --source-dir force-app --target-org pkgorg [[/code]]

Then upload again as Managed — Beta, version 1.0 (Salesforce increments the internal build) or bump to 1.1. Re-install into a fresh customer org — you cannot upgrade from a beta, so betas are always fresh installs.

Step 11 — Release version 1.0

You (UI): Upload → Version Name 1.0 GA → Version Number 1.0 → Managed — Released.

Salesforce: runs all Apex tests in the packaging org and blocks the upload below 75% coverage Documented; then mints a permanent 04t.

Point of no return #2. This version is now immutable and undeletable, and your global API surface is frozen. Do not do this until Step 8's checklist passed.

Verify: the version row shows status Managed — Released; install it into a brand new customer-like org and repeat the customer checks.

Step 12 — Ship 1.1 and perform an upgrade

  1. Add something additive — e.g. a new field Resolution_Notes__c and a new global method. Nothing removed, nothing renamed.
  2. Deploy to the packaging org, Add Components for the new field, run tests.
  3. Upload as Managed — Released, Version Number 1.1.
  4. In the customer org that already has 1.0 (the released one), install the 1.1 04t: [[code bash]] sf package install --package 04t...11 --target-org customer1 \ --installation-key "LearnPackaging123" --wait 20 --no-prompt sf package installed list --target-org customer1 # should now show 1.1 [[/code]]
  5. Verify the point of the whole exercise: the Service Request records you created under 1.0 are still there, with their data, and the new field exists and is empty. Metadata upgraded, data preserved.

What you should be able to explain now

  • Why the namespace org and the packaging org are the same org in 1GP
  • What Salesforce reads to decide what goes into a version
  • Why a beta cannot be upgraded from
  • What the 75% coverage gate applies to, and when it is enforced
  • Why you must install into a non-namespaced org you never pushed source to
  • What a patch org is and why merging the fix forward is your responsibility
  • Three things you can never change after Step 11
