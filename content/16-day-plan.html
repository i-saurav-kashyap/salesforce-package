Fourteen days, each about 2–4 focused hours. Do not start a day until the previous day's verification passes. If a day takes two days, take two days — the sequence matters, the calendar does not.

Every day has the same shape: objective → concepts → hands-on → commands → expected output → verification → common mistakes → what you can explain. The final line of each day is the one that matters: if you cannot say it out loud, you have not finished the day.

Day 1 — Environment and vocabulary

Objective: a working toolchain and two authenticated orgs.
Concepts: org, DE org, Dev Hub, namespace, package, 1GP vs 2GP (names only).
Hands-on: Stage 0 in full.
Commands: npm i -g @salesforce/cli, sf org login web, sf org list, sf project generate, sf org create scratch.
Expected output: a scratch org opens in your browser.
Verification: the Stage 0 checklist, all ticks.
Common mistakes: both sfdx and sf installed; Dev Hub not enabled; scratch org creation failing on a bad feature name.
Explain: what a Dev Hub is and why 1GP does not need one.

Day 2 — Org architecture and the namespace decision

Objective: decide and record your org architecture; register nothing yet.
Concepts: PBO, Dev Hub, namespace org, packaging org, scratch org, install-test org.
Hands-on: read Part 2; fill in the decision table in Part 3 §D; check namespace availability candidates (do not save yet).
Verification: a written list of which org plays which role, and three candidate namespaces.
Common mistakes: planning to use one org for everything; choosing a namespace like test1.
Explain: what is lost if each org disappears.

Day 3 — Build the application (part 1)

Objective: the data layer works in a scratch org.
Concepts: objects, fields, validation rules, list views, CMDT, custom labels.
Hands-on: deploy packages/core's objects, CMDT, labels and tab; create records by hand.
Commands: sf project deploy start, sf org assign permset, sf apex run --file scripts/apex/seed-data.apex.
Verification: you can create a Service Request; the validation rule fires; the CMDT row is queryable.
Common mistakes: forgetting the permission set and then blaming the deploy.
Explain: why the SLA default is Custom Metadata and not a hard-coded constant.

Day 4 — Build the application (part 2)

Objective: Apex + LWC + tests, all green.
Concepts: service/selector layering, global vs public, user mode, LWC wire adapters.
Hands-on: deploy the classes and the LWC; put the console on an app page; run the tests.
Commands: sf apex run test --code-coverage --result-format human.
Verification: all tests pass, coverage >75%, the console lists and completes requests.
Common mistakes: marking everything global; forgetting classAccesses in the permission set.
Explain: what global commits you to forever.

Day 5 — 1GP: namespace, package, first beta

Objective: a 1GP beta exists and installs.
Concepts: packaging org, component list, upload, beta.
Hands-on: Part 6 steps 1–8.
Verification: a 04t exists; it installs into a clean org; a non-admin user with only your permission set can use the app.
Common mistakes: deploying a component but not adding it to the package.
Explain: what Salesforce reads to decide what is in a 1GP version.

Day 6 — 1GP: release and upgrade

Objective: feel the irreversibility.
Hands-on: release 1.0; install it; build an additive 1.1; upgrade the same org; confirm data survived.
Verification: records created under 1.0 still exist after upgrading to 1.1.
Common mistakes: releasing before install-testing; trying to change a global signature in 1.1.
Explain: three things you can never change after a release, and why patches need their own org.

Day 7 — 2GP: Dev Hub, namespace link, first package

Objective: two 0Ho package definitions.
Hands-on: link the namespace registry; sf package create for Core and Field Ops; inspect the diff in sfdx-project.json.
Verification: sf package list --verbose shows both; aliases committed.
Common mistakes: namespace not linked; namespace string mismatch; 2GP not enabled in the Dev Hub.
Explain: which Dev Hub objects now hold your package identity.

Day 8 — 2GP: versions, install, promote

Objective: a released 2GP version installed in a customer-like org.
Hands-on: Part 8 steps 5–8; keep the failed attempts and read them with sf package version create report.
Verification: sf package version list --released shows your versions; install works in a non-namespaced org.
Common mistakes: forgetting --code-coverage and then being unable to promote.
Explain: the full journey from 08c to 04t.

Day 9 — Ancestry and upgrades

Objective: a real upgrade path.
Hands-on: add ancestorVersion; build 1.1; upgrade a customer org that has 1.0; then deliberately build a version without ancestry and observe the difference.
Verification: upgrade succeeds and data is preserved.
Common mistakes: forgetting ancestry until customers exist.
Explain: why 2GP needs ancestry and 1GP does not.

Day 10 — Dependencies A → B (→ C)

Objective: a working, enforced dependency.
Hands-on: Part 11 A: declare the dependency, build B, install in the wrong order on purpose, then the right order. Optionally add package C.
Verification: B refuses to build without the declaration; B refuses to install without A.
Common mistakes: leaving LATEST on a release branch.
Explain: what happens inside the build environment when a dependency is declared.

Day 11 — 1GP → 2GP dependency, and the graph

Objective: a 2GP package depending on your own 1GP package.
Hands-on: Part 11 B and C; inspect everything with sf package version report --verbose and sf package version displayancestry.
Verification: the 2GP builds against the 1GP 04t and installs in the right order.
Common mistakes: depending on a beta 1GP version.
Explain: why the reverse direction does not exist, and what a circular dependency really means.

Day 12 — Customer simulation: the seven install tests

Objective: break your own product the way customers will.
Hands-on: the Part 12 test matrix, all seven, especially the failed upgrade.
Verification: you can produce, and then explain, a failed upgrade and a failed dependency install.
Common mistakes: testing only as a System Administrator.
Explain: what upgrade does to data, deleted metadata, layouts and permission sets.

Day 13 — Security

Objective: a clean scan and a security-literate codebase.
Hands-on: Part 13: add VulnerableDemo, scan, fix all eight findings, delete the file, re-scan; then walk the readiness checklist against your real code.
Verification: scan clean at your threshold; every checklist item ticked or justified in writing.
Common mistakes: assuming with sharing covers FLS.
Explain: CRUD vs FLS vs sharing, in one paragraph each.

Day 14 — CI/CD, AppExchange, and the exam

Objective: hands off the keyboard for releases; know the commercial path.
Hands-on: set up JWT auth and both workflows from Part 14; open a PR and watch it validate; read Part 15; then take the final test.
Verification: a PR goes green without you touching an org; a release workflow produces a 04t.
Common mistakes: secrets in the repo; scratch orgs leaked by failed jobs.
Explain: the entire chain from a commit to a customer's org, out loud, in under three minutes.
