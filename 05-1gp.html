Part 5

1GP From Absolute Zero

Forget 2GP for the next two pages. We build a first-generation managed package the way ISVs did for fifteen years — because you will meet 1GP packages for the rest of your Salesforce career, and because 2GP only makes sense once you have felt what it fixed.

Salesforce's current recommendation: use 2GP for new managed packages. 1GP here is for understanding, and for working on existing products (Sitetracker's main package, for example, is 1GP). Do not launch a new AppExchange product on 1GP without a deliberate reason.

The 19 questions, answered

1. Which org creates the namespace?

A Developer Edition org. Nothing else can register a namespace. You do it in Setup → Package Manager → Developer Settings → Edit. Documented It is permanent and globally unique.

2. Which org becomes the packaging org?

That same org. In 1GP the namespace org and the packaging org are the same DE org — there is no separate concept. The moment you create a managed package in it, that org is your product's home forever.

3. How do I create/register the namespace?

  1. Log into the DE org you reserved for this (not your Dev Hub).
  2. Setup → quick find “Package Manager” (older orgs: “Packages”).
  3. In the Developer Settings panel click Edit, then Continue.
  4. Type a candidate namespace (1–15 chars, starts with a letter, letters/numbers/underscores, no consecutive or trailing underscores) and click Check Availability.
  5. When one is available, Review Your Selection → Save.

There is no undo. Salesforce warns you on this screen; believe it. Use a name you would be happy to see in a customer's org in ten years: opskit, not test01.

4. How do I create the 1GP managed package?

In the same org: Setup → Package Manager → Packages → New. Give it a name and a description, and tick Managed. (Until the namespace is registered, the Managed option is not available.) There is no supported CLI command to create a 1GP package — it is a UI action. Documented

5. Where do I create metadata?

Two legitimate models:

  • Develop-in-the-packaging-org (classic). You build objects/classes directly in the org, then retrieve them into Git for backup. Simple, and how many legacy products ran for years.
  • Develop-elsewhere, deploy-in (better). You develop in a scratch/DE org from Git and deploy into the packaging org before uploading. This is what the course does.

6. Where does the source of truth live?

The packaging org. Whatever is in it (and added to the package) is what ships. Git is a copy, and a copy can silently drift — someone edits a field in the packaging org UI and Git never learns. That drift is the defining pain of 1GP.

7. How do I connect my local project to the packaging org?

bash
cd sample-project/1gp
sf org login web --alias pkgorg           # the DE org that owns the namespace
sf org display --target-org pkgorg
sf project deploy start --source-dir force-app --target-org pkgorg

What that deploy does: the CLI zips your metadata, calls the Metadata API deploy(), and the org compiles/creates the components. Because the org has a namespace, the components become opskit__Service_Request__c and so on inside the org — your local files stay unprefixed. That asymmetry is normal and correct.

8. How do I add components to the package?

Setup → Package Manager → Packages → your package → Add Components. Choose a component type, tick the components, click Add. Salesforce then pulls in dependent components automatically (adding an Apex class adds what it references; adding an object adds its fields).

The classic 1GP bug: you deploy a new field, forget to add it to the package, upload, and the customer's install is missing a field your code references. Always re-open the package's component list before uploading and compare it against what you deployed. The View Dependencies button on the upload screen is your friend.

9. How do I create a package version?

UI: Package Manager → your package → Upload. Give it a Version Name (“Winter Release”), Version Number (1.0), optionally a password (installation key), and choose Managed — Beta or Managed — Released. CLI equivalent:

bash
# Uploads (creates a version of) an existing 1GP package.
sf package1 version create \
  --package-id 033xx0000004Cxx \
  --name "Winter Release" \
  --version "1.0" \
  --managed-released \        # omit this flag to produce a BETA
  --installation-key "LearnPackaging123" \
  --wait 20

# Watch / list
sf package1 version create get --request-id 0HDxx...      # status of the upload request
sf package1 version list --package-id 033xx0000004Cxx     # all versions, with their 04t IDs

Which org: the packaging org (--target-org pkgorg). Which API: the Tooling API PackageUploadRequest object — the CLI inserts a record and polls it. Documented What you get: a 04t subscriber package version ID and an install URL.

10. How does Salesforce determine what is inside the package?

By reading the package's component list in the packaging org at upload time, plus everything those components depend on. There is no manifest in your repo; there is no build from source. The org's current state is the input. Inference This is precisely why 1GP cannot support parallel feature branches: an org has one state at a time.

11. What is the package version ID?

The 04t... (SubscriberPackageVersion) ID minted by the upload. It is what goes in an install URL: https://login.salesforce.com/packaging/installPackage.apexp?p0=04t.... The 033... ID identifies the package; customers never need it.

12. What is a beta package?

An upload marked Managed — Beta. Installable only in scratch orgs, sandboxes, DE orgs and Trialforce source orgs — never production. Not upgradeable: a beta cannot be upgraded to a later version, and no customer can upgrade from it. Use betas freely; that is what they are for.

13. What is a released package?

Managed — Released. Installable anywhere, permanently part of your upgrade lineage, undeletable and unmodifiable. After your first released version, your namespace, package name, global API surface and object schema are commitments.

14. What changes are allowed after release?

ChangeAllowed?Notes
Add a new component (object, field, class, LWC)✔The normal way to grow
Add a method to an existing global class✔Adding is fine
Change public Apex freely✔Invisible to subscribers
Add a picklist value✔But see “restricted picklist” caveats on upgrade
Change a field label / help text✔Cosmetic
Change component behaviour✔Your job is to not break customers
Deprecate a global method (@Deprecated)✔It still exists, just hidden from new code

15. What cannot be changed?

ChangeAllowed?Why
Remove or rename a global Apex method/class/interface✘Subscriber and partner code may call it
Change a global method signature or return type✘Same reason
Make global → public✘Reducing visibility breaks callers
Delete a released custom object or field✘ (effectively)Subscriber data lives in it. You deprecate, you do not delete
Change a field's data type / length downward✘ mostlyExisting data would be invalidated
Change the namespace✘Everything is prefixed with it
Delete or replace a released version✘Customers may be running it
Un-release a version✘—

Verify The precise list of “allowed changes to released managed components” is long and version-specific. Before any risky change, check the current “Editing Components After Release” table in the packaging docs. When in doubt, test the upgrade in a scratch org that has the older version installed — that test is the ground truth.

16. How does package upgrade work?

The subscriber installs a newer 04t of the same package. Salesforce diffs the installed version against the new one and applies additions/changes to metadata only; the subscriber's data is untouched. Components you removed from the package are not deleted from the subscriber org — they are simply no longer upgraded (they linger). Upgrades are transactional at the platform level: if it fails, it rolls back. Detail: Part 12.

17. How do patches work?

1GP A patch is a version that changes only the third digit (1.2 → 1.2.1) and may contain only a restricted set of changes — bug fixes, not new schema. Mechanically:

  1. In the packaging org: Package Manager → Patch Organizations → New, choosing the released version you want to patch. Salesforce creates a patch development org which is a copy of the packaging org at that version.
  2. You fix the bug in the patch org (deploy from Git).
  3. You upload from the patch org, producing 1.2.1.
  4. The fix must also be merged forward into the main packaging org, or your next major release regresses it.

That last step is manual and is exactly the kind of thing 1GP shops get wrong. Verify the current restrictions on what a patch may contain — they are tighter than most people assume (for example, new components are generally not allowed).

18. What happens when a customer installs the package?

Summarised here, detailed in Part 12: Salesforce validates the version, resolves dependencies, shows the component list and the security/access choice, then creates all components in the subscriber org under your namespace, runs your InstallHandler (post-install script) if you have one, and records the install against your LMA.

19. How does namespace isolation work?

  • Every packaged component gets the prefix: opskit__Service_Request__c, opskit.ServiceRequestService, label opskit__Ops_Request_Created.
  • Your Apex executes in your namespace context: unqualified references inside your code resolve to your components first, so a subscriber's Status__c cannot shadow yours.
  • Subscribers cannot view or edit your Apex (unless it is a global interface they implement).
  • Some limits are tracked per namespace Inference — a well-known example is that your packaged Apex gets its own SOQL/DML governor allocation separate from the subscriber's code in many contexts. Verify the exact behaviour before you design around it.
  • Dynamic code is where isolation leaks: Database.query('SELECT ... FROM Service_Request__c') resolves fine inside your namespace, but a hard-coded 'opskit__Service_Request__c' string in a non-namespaced context, or a subscriber-supplied field name, will bite you. Test in a real install.

1GP mental model, in one diagram

  Your laptop / Git                  PACKAGING ORG (DE, namespace = opskit)
  ─────────────────                  ────────────────────────────────────────
  force-app/**  ──deploy──►  components exist in the org (opskit__ prefixed)
                                          │
                                          │  you tick them in
                                          ▼
                                   PACKAGE  (033…)  = a component LIST
                                          │
                                          │  Upload (UI) / sf package1 version create
                                          ▼
                              PACKAGE VERSION (04t…)  ── beta or released
                                          │
                                          ▼
                              install URL → any org

The thing to internalise: the package is a list of components in an org, and a version is a snapshot of that org. Nothing about your Git history is visible to Salesforce. When we get to 2GP, the package becomes a folder in your repo and the version becomes a build of your source. Everything else follows.
