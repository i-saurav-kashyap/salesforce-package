The diagnostic playbook

Copy-paste blocks. Run the one for the layer that failed.

“Which org am I actually talking to?”

bash
sf org list --all
sf config list                       # project + global defaults
sf org display --target-org dev1
sf data query --target-org dev1 --query "SELECT Id, Name, OrganizationType, NamespacePrefix, \
InstanceName, IsSandbox FROM Organization"

Scratch org creation failed

bash
sf data query --target-org devhub --query "SELECT SignupUsername, Status, ErrorCode, Description, \
CreatedDate FROM ScratchOrgInfo ORDER BY CreatedDate DESC LIMIT 5"
sf org list limits --target-org devhub
sf data query --target-org devhub --query "SELECT SignupUsername, ExpirationDate, CreatedBy.Name \
FROM ActiveScratchOrg ORDER BY CreatedDate"

Deployment failed

bash
sf project deploy report --target-org dev1                  # full result of the last deploy
sf project deploy preview --target-org dev1                 # what would go, what conflicts
sf project deploy start --dry-run --target-org dev1         # validate without saving
sf project retrieve preview --target-org dev1               # what changed in the org

Package version build failed

bash
sf package version create list --target-dev-hub devhub                    # recent attempts
sf package version create report --package-create-request-id 08c... -v devhub
sf data query --target-org devhub --use-tooling-api --query \
"SELECT Id, Status, Error, Package2Id, CreatedDate FROM Package2VersionCreateRequest \
ORDER BY CreatedDate DESC LIMIT 5"

Install / upgrade failed

bash
sf package install report --request-id 0Hf... --target-org customer1
sf package installed list --target-org customer1
sf package version report --package "Ops Toolkit Field Ops@1.0.0-1" -v devhub --verbose  # its dependencies
sf data query --target-org customer1 --use-tooling-api --query \
"SELECT SubscriberPackage.Name, SubscriberPackageVersion.MajorVersion, \
SubscriberPackageVersion.MinorVersion, SubscriberPackageVersion.Id FROM InstalledSubscriberPackage"

Runtime failure — get the logs

bash
sf apex tail log --target-org customer1                     # live stream while you reproduce
sf apex get log --target-org customer1 --number 1           # most recent log
sf apex run test --target-org customer1 --tests MyTest --result-format human
sf apex run --file scripts/apex/probe.apex --target-org customer1   # ad-hoc probing

Reading a debug log without drowning

A raw Apex log is thousands of lines. You almost never read it top to bottom.

  1. Set the levels first. Setup → Debug Logs → new trace flag. Turn Apex Code = FINEST and Database = FINEST, and everything else to ERROR — noise from Workflow and Validation drowns the signal (though set Validation = INFO when hunting a rogue validation rule).
  2. Search for the exception first, not the beginning: FATAL_ERROR, EXCEPTION_THROWN, |FATAL|.
  3. Then read upward from the exception to the last CODE_UNIT_STARTED — that tells you whose code you were in when it died. In a subscriber org, this is how you discover you were inside their trigger.
  4. For limits, jump to LIMIT_USAGE_FOR_NS at the end. It reports usage per namespace, so you can see whether the SOQL was yours or theirs.
  5. For “why did nothing happen”, search CODE_UNIT_STARTED to confirm your code ran at all — half of these mysteries are code that never executed.
bash
sf apex get log --target-org customer1 --number 1 > log.txt
grep -n -E "FATAL_ERROR|EXCEPTION_THROWN|LIMIT_USAGE_FOR_NS" log.txt | head -20
sed -n '/LIMIT_USAGE_FOR_NS/,$p' log.txt | head -40      # the limits summary block

The LIMIT_USAGE_FOR_NS block is the ISV's best friend. It breaks limit consumption down by namespace, which settles the “is it your package or ours?” argument with a customer in about thirty seconds.

Debugging inside a subscriber org

You cannot log into a customer's org whenever you like. The supported route:

  1. The customer grants login access to your support organisation (their Setup → Grant Account Login Access), or your License Management App subscriber support access is enabled.
  2. From the LMA in your PBO, open the Subscribers list and log in to their org in a support context.
  3. You can inspect setup and run debug logs on your own packaged code; you generally cannot see their unpackaged Apex source, and your access is limited and audited. Verify exactly what subscriber support access permits in the current ISVforce Guide — the boundaries matter legally, not just technically.

When you cannot get in at all, ask the customer for exactly these five things — it converts a week of guessing into an afternoon:

  • The full error text and the time it happened, with their time zone
  • Their org ID, edition, and whether it is production or sandbox
  • The output of Setup → Installed Packages (your version and every other vendor's)
  • A debug log of the failing action, with Apex Code = FINEST
  • Whether it fails for all users or one profile, and for all records or specific ones

That last question is the highest-value one on the list: “all users” points at code or data, “one profile” points at permissions, and “specific records” points at sharing or data shape.

Prevention checklist — the ten habits that remove most of this page

  • Always pass --target-org / --target-dev-hub explicitly in anything committed
  • One CLI installed; never sfdx v7 alongside sf v2
  • Deploy whole package directories, never subsets, and verify from a clean clone
  • Every test creates its own data; no SeeAllData; no reliance on seed scripts
  • --code-coverage on every version create, without exception
  • Declare the dependency in the same commit as the first cross-package reference
  • Install-test in a non-namespaced org, at your lowest supported edition, as a non-admin user
  • Rehearse the upgrade from the previous release with deliberately messy data
  • Never hard-code an API name where a Schema describe would do
  • CI deletes every org it creates with if: always(), and secrets never reach the repo

When you are genuinely stuck, a Partner Support case moves fastest when it contains: the exact command and its --json output, the relevant record ID (08c/0Hf/ScratchOrgInfo), the org IDs involved, what you expected, what you observed, and what you already ruled out. “Package creation fails” gets a request for information; the list above gets an answer.
