This site is your course. It takes you from an empty laptop to a working AppExchange-style product: an application you build, package as 1GP and 2GP, version, make depend on other packages, install as a customer, upgrade, harden for Security Review, automate in CI, and list on AppExchange.

How to use this site. Work the pages in order. Each page ends with verification steps. Do not move to the next stage until the current stage's verification passes — packaging mistakes are cheap to fix on day 2 and expensive to fix after a version is released, because a released managed package version can never be deleted or altered (beta versions can still be deleted). If you opened these files directly in the browser (file://), Copy buttons work more reliably when you serve the folder instead: python3 -m http.server from this directory, then visit http://localhost:8000.

The one sentence that explains the whole difference. In 1GP, the packaging org holds the truth and Git is a backup. In 2GP, Git holds the truth and every org — including the build environment Salesforce spins up to create the version — is disposable. Everything else in this course follows from that.

2 · The minimum orgs you need

Full detail, including who owns each org and what happens if it disappears, is on Org architecture. The short answer:

#OrgWhy you cannot skip it1GP2GP
1Partner Business Org (PBO)
from the Salesforce Partner Program		The only place you get Partner Console / Publishing, Environment Hub, and the ability to submit a Security Review. For a real product you enable Dev Hub here.✔ (for listing)✔ (Dev Hub + listing)
2Namespace org (Developer Edition)A namespace is 1–15 characters, globally unique, registered in exactly one org, and cannot be renamed or reused. 2GP keep this org empty — its job is only to own the namespace. 1GP this is the packaging org, so it also holds the package metadata.✔ this org IS the packaging org✔ linked to Dev Hub as a Namespace Registry
3Scratch orgsWhere you actually develop and where you test installs. They live 1–30 days (--duration-days), then expire. Create them as you need them; delete them when you are done so you do not burn the daily/active limits.optional✔ core to the workflow
4Install-test / customer-like orgYou must install your package into an org that never saw your source, or you will ship broken permissions and namespace bugs.✔✔

Absolute minimum to start this course today: two free Developer Edition orgs plus the sf CLI. Org 1 is the learning Dev Hub. Org 2 owns the namespace (and later doubles as the 1GP packaging org). You can build, version, install, upgrade, and run CI with that. You need a Partner Business Org only for Security Review (Part 13) and AppExchange listing (Part 15) — and for that your company must join the Salesforce Partner Program. Verify Partner Program eligibility and whether your company already has a PBO before signing up for one.

You can register a namespace in the same DE you use as Dev Hub. This course does not: Salesforce's 2GP docs want a separate namespace org, and keeping nsorg empty prevents the most common first-week mistake (dumping sample data into the org that must stay pristine).

A Developer Edition Dev Hub is tiny. Documented A DE or trial Dev Hub allows 3 active scratch orgs and 6 successful creates per rolling 24 hours, plus a similarly low daily cap on package versions. Package versions are bound to that Dev Hub: if the DE is deactivated, you lose the ability to create new versions of packages born there. Fine for learning; never use a throwaway DE as the Dev Hub of a real product. Check remaining quota with sf org list limits --target-org devhub and look at ActiveScratchOrgs / DailyScratchOrgs.

5 · Stage 0 — your first practical exercise

Nothing here creates a package yet. Stage 0 exists so that when you reach Stage 1 you are not debugging authentication instead of learning packaging.

0.1  Install the local toolchain

Pick one install method and stick to it. Mixing the OS installer with npm is a classic PATH mess. Active Node LTS (22 or 24) if you use npm; the OS installer bundles its own Node.

[[code bash]] # --- macOS / Linux, npm method ------------------------------------------ # Node: Active LTS (22 or 24). Git is required either way. brew install node git # or: https://nodejs.org (Windows: Git for Windows) npm install --global @salesforce/cli # --- alternative: OS installer (bundles Node, no brew) ------------------ # macOS/Windows pkg/exe: https://developer.salesforce.com/tools/salesforcecli # Then use `sf update` to stay current (npm installs use npm, not sf update). sf --version # expect @salesforce/cli/2.x sf package --help >/dev/null # packaging is often a JIT plugin; this is the real check # Optional sf plugins install @salesforce/plugin-packaging # only if `sf package --help` fails code --install-extension salesforce.salesforcedx-vscode [[/code]]

Windows: install Git for Windows and either the Salesforce CLI .exe or Node LTS then npm install --global @salesforce/cli. Heredocs in later steps (<<'APEX') are bash; in PowerShell use a file: sf apex run --target-org devhub --file hello.apex.

Do not install the old sfdx CLI alongside sf. Two CLIs sharing ~/.sfdx is the single most common source of “my org is authenticated but the command says it isn't”. If sfdx --version prints 7.x: npm uninstall --global sfdx-cli removes only an npm install. If you used the old .pkg / .exe installer, uninstall that from the OS as well. sf v2 still accepts most sfdx-era commands.

Java is not required for the CLI itself. You only need a JDK if you run Salesforce Code Analyzer scanners that still shell out to PMD / Graph Engine — which you will in Part 13. Verify Code Analyzer versions change their Java requirement; check the plugin's docs when you install it.

0.2  Get your first two orgs

  1. Sign up for a Developer Edition org at developer.salesforce.com/signup. Use an email you control forever. The username (not necessarily the inbox) should be recognisable in a year, e.g. you+devhub@example.com — Gmail-style plus-addressing is fine if your mail host supports it. This org will be your Dev Hub for learning. DE orgs are free and have small storage limits. They can be deactivated for inactivity, so log in occasionally. Documented
  2. Sign up for a second Developer Edition org. This one will own your namespace. Keep it clean: no experiments, no sample data, no developing in it. Username e.g. you+ns@example.com. Log in every few months so the org is not deactivated — if it dies, you cannot create new versions in that namespace until Partner Support recovers it. Documented A namespace is permanent and org-bound: you cannot rename or reuse it. You can later link the same namespace org to a different Dev Hub (that is how 2GP package transfer starts).
  3. Find out whether your company already has a Partner Business Org. Ask internally, or check partners.salesforce.com. Do not create a duplicate PBO; listings and Security Reviews are tied to the company account.

0.3  Authenticate and prove it works

[[code bash]] mkdir -p ~/sf-learning && cd ~/sf-learning # Git will refuse the first commit without identity. Skip if already set. git config --global user.name "Your Name" # use your real name git config --global user.email "you@example.com" # 1) Log in to the org that will be your Dev Hub sf org login web --alias devhub --set-default-dev-hub # 2) Log in to the org that will own your namespace sf org login web --alias nsorg # 3) Prove both are stored locally sf org list --all sf org display --target-org devhub # 4) Prove you can actually run code in the org (round-trips through the Apex API) sf apex run --target-org devhub <<'APEX' System.debug('Hello from ' + UserInfo.getOrganizationName()); APEX [[/code]]

What each command talks to: org login web opens the browser to your org's OAuth endpoint and stores a refresh token locally — it does not store your password. org list reads only local files. org display calls the org to confirm the token still works. apex run executes anonymous Apex through the Tooling API.

0.4  Enable Dev Hub

  1. In the devhub org: Setup → quick find “Dev Hub” → Dev Hub → toggle Enable Dev Hub. This cannot be turned back off. Documented Dev Hub is available in Developer, Enterprise, Performance, and Unlimited editions, and in Partner Business Orgs.
  2. Same page: enable Unlocked Packages and Second-Generation Managed Packages. Without this, sf package create fails. (This course builds managed 2GP, not unlocked packages; the toggle still has to be on.)
  3. Verify from the CLI — this is the real test, not the toggle: [[code bash]] sf org list --all # devhub should show as (D) default dev hub sf org list limits --target-org devhub sf data query --target-org devhub --query "SELECT Id FROM ScratchOrgInfo LIMIT 1" [[/code]] If the query returns a result set (even empty) rather than sObject type 'ScratchOrgInfo' is not supported, Dev Hub is on. list limits should show ActiveScratchOrgs remaining 3 of 3 on a DE.

0.5  Create your first scratch org (the real proof)

[[code bash]] sf project generate --name ops-toolkit --template standard cd ops-toolkit git init && git add -A && git commit -m "chore: empty DX project" sf org create scratch \ --definition-file config/project-scratch-def.json \ --alias dev1 \ --duration-days 7 \ --wait 10 \ --set-default sf org open --target-org dev1 [[/code]]

Behind the scenes: the CLI inserts a ScratchOrgInfo record into your Dev Hub; Salesforce's org-provisioning service builds a brand-new org from your definition file, applies the requested edition/features/settings, and returns login credentials; the CLI then authenticates to that new org and saves it under the alias dev1. Full walk-through: Behind the scenes.

When you are done with a scratch org, sf org delete scratch --target-org dev1 --no-prompt returns an active slot. On a DE Dev Hub you only have three.

Stage 0 verification — tick every box before Stage 1

  • sf --version prints @salesforce/cli/2.x and no sfdx 7.x exists on your PATH
  • sf org list --all shows devhub marked as the default Dev Hub
  • sf apex run against devhub returns success
  • Dev Hub is enabled, and Unlocked/2GP packages are enabled, in the Dev Hub org
  • sf org list limits --target-org devhub shows scratch-org quota (3/6 on a DE)
  • A scratch org dev1 was created and sf org open logs you into it
  • You have a second DE org reserved, untouched, to own your namespace
  • You know whether your company has a Partner Business Org (and who administers it)
  • Git user.name / user.email are set and the DX project is committed

Stop here. When those boxes are ticked, you are ready for Stage 1: the namespace and the application itself (The app, after Big picture through Prerequisites). If you are working with a tutor, say “Stage 0 done” and paste any errors.
