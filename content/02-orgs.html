“You need several orgs” is useless advice. Here is exactly which orgs exist, who creates each one, who owns it, how you authenticate, what is stored in it, how long it lives, and what breaks if it disappears.

Org-by-org deep dive

Partner Business Org

Who creates itSalesforce, when your company is approved into the Partner Program (partners.salesforce.com). Not something an individual spins up.
Who owns itYour company. Usually administered by an ISV ops / alliances team.
How you authenticateNamed user + MFA in the browser; sf org login web --alias pbo for CLI work.
What is storedPublishing Console data (Provider, Solutions, Listings), Environment Hub org list, LMA licence records, Trialforce config, and often the Dev Hub.
Who interactsProduct/marketing (listing), engineering leads (Dev Hub, Security Review submissions), support (subscriber access).
LifetimeAs long as the company sells the product.
If it disappearsCatastrophic-but-recoverable-with-Salesforce: listings, licence records and Security Review history live here. There is no self-service rebuild — you open a Partner Support case. Verify

Dev Hub

Who creates itYou, by toggling Setup → Dev Hub → Enable Dev Hub in an existing org (PBO for real products; a free DE org for learning).
Who owns itThe org's owner. Developers need the Create and Update Second-Generation Packages permission plus API access.
How you authenticatesf org login web --alias devhub --set-default-dev-hub. For CI: a JWT bearer flow with a Connected App and a private key — never a password.
What is storedScratchOrgInfo (every scratch org you ever made), Package2, Package2Version, Package2VersionCreateRequest, namespace registry links.
LifetimePermanent. Enabling is irreversible.
If it disappearsYou lose the ability to create new versions of your 2GP packages. Existing installed versions keep working for customers (the 04t lives in Salesforce's package infrastructure, not in your Dev Hub) Inference, but you cannot ship an upgrade. Treat the Dev Hub as production infrastructure.

Learning trap: do not enable Dev Hub in a throwaway org you will abandon, then create your real packages there. Package identity is bound to that Dev Hub. Choose the Dev Hub org deliberately — for a real product, the PBO.

Namespace org (Developer Edition)

Who creates itYou: developer.salesforce.com/signup.
How the namespace gets thereIn that org: Setup → Package Manager (older UI: “Packages”) → Edit next to Developer Settings → enter and check a namespace → Review → Save. Documented Irreversible.
What is storedThe namespace registration. For 1GP, also the entire package. For 2GP, nothing else — keep it empty and pristine.
How 2GP uses itYou link it to the Dev Hub once: sf org login web --alias nsorg then, in the Dev Hub UI, Namespace Registries → Link Namespace (or sf package:create fails with “namespace not linked”).
LifetimeForever. Log in occasionally so it is not deactivated for inactivity.
If it disappears2GP: you can no longer create versions in that namespace; recovery means a Partner Support case Verify. 1GP: you have lost the package. This is why 1GP shops guard the packaging org like a production database.

1GP packaging org 1GP

Who creates itYou — it is simply the DE org where you registered the namespace and then created a package in Package Manager.
What is storedThe package definition and every component in it. Uploaded versions are snapshots of this org's state.
How you interactBrowser (Package Manager, Upload) plus metadata deploys from your laptop: sf project deploy start --target-org pkgorg.
Who else touches itIdeally nobody. Every developer deploying straight into it is how 1GP orgs rot.
LifetimeThe life of the product.
If it disappearsYou cannot create another version of that package, ever. Customers keep what they installed. Mitigation: keep a full metadata retrieve in Git and back it up; the org itself is still irreplaceable.

Scratch orgs

Who creates themThe Dev Hub, on your request: sf org create scratch.
How you authenticateAutomatically — the CLI receives credentials and stores an alias. No password to manage.
What is storedOnly what you push plus test data. Treat everything in a scratch org as disposable.
Lifetime1–30 days (--duration-days). They die silently; that is the point.
If one disappearsNothing is lost if you have been committing. If losing a scratch org hurts, your process is wrong.

Install-test org (customer-like)

A scratch org (or spare DE org) that has never had your source pushed into it. You install the 04t and use the app. This is the only way to catch:

  • components you forgot to add to the package (they exist in your dev org, so it “works” there),
  • permission sets that don't actually grant access to packaged objects,
  • namespace-sensitive code (hard-coded field names without the namespace, dynamic SOQL, JS referencing API names),
  • missing dependencies.

Rule: ship nothing you have not installed into a clean org and clicked through as a non-admin user.

QA / UAT / demo orgs

Longer-lived orgs where a specific released version sits still while people test or demo it. They usually contain realistic data, which is exactly what a scratch org is bad at. Created from the Environment Hub (partner DE/enterprise-edition test orgs) or as long-duration scratch orgs. Verify which test-org types your partner tier entitles you to.

Subscriber org

You never build here. You can, with the customer's consent, use Subscriber Support from the LMA to log in read-mostly and debug. Expect: other managed packages, different profiles, large data volumes, custom validation rules that break your DML, and field-level security that hides fields your code assumes.

Minimum setup (learning — what you will use in this course)

[[diagram]] DE org #1 ── Dev Hub enabled (alias: devhub) │ └── creates scratch orgs, owns the 2GP packages │ DE org #2 ── namespace registered (alias: nsorg) │ └── linked to devhub as a Namespace Registry │ └── ALSO used as the 1GP packaging org for the learning exercise │ scratch: dev1 (namespaced, 7 days) ← daily development scratch: test1 (NON-namespaced, 1 day) ← install the 04t here [[/diagram]]

Two permanent free orgs, plus disposable scratch orgs. Total cost: nothing.

Course simplification, stated plainly: using the same DE org as both the 2GP namespace org and the 1GP packaging org is fine for learning and lets you compare the two models with one namespace. In a real company you would use separate namespaces (e.g. opskit for 2GP, opskitlegacy for the 1GP exercise), because a namespace already in use by a released 1GP package brings its own constraints. Verify the current rules for reusing a 1GP namespace for 2GP packages — Salesforce supports it (that is how ISVs migrate), but the constraints around ancestry and shared namespaces are worth confirming for your exact case.

Team conventions worth copying

  • One Dev Hub per company, not per team. Package identity should not depend on who set it up.
  • Nobody develops in the namespace org. Its only job is to exist.
  • CI owns scratch org creation; developers create their own only for local work.
  • Every released version is a Git tag and the 04t is recorded in the repo (sfdx-project.json package aliases do this automatically — commit them).
  • The install-test org is non-namespaced, so you experience your own namespace prefixes exactly as a customer does.
  • Dev Hub auth in CI is JWT with the private key in a secret store, never a username/password.

  • You can explain why losing a 1GP packaging org is worse than losing a Dev Hub
  • You can explain why the install-test org must be non-namespaced
  • You have decided which org will be your Dev Hub and which will own your namespace — and written it down
