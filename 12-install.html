Part 12

Customer Install and Upgrades

You are the customer now. This page makes you install, break, upgrade, fail, uninstall and reinstall your own product — because every one of those is a support ticket you will otherwise receive from a real customer.

Installation

The flow

 Customer org
      │
      ▼
 Install URL:  https://login.salesforce.com/packaging/installPackage.apexp?p0=04t…
      │        (sandbox:  https://test.salesforce.com/packaging/…)
      ▼
 1. Salesforce validates the version   → is it released? does the key match? edition/features OK?
      ▼
 2. Dependency resolution              → are required packages present? if not: FAIL, naming the 04t
      ▼
 3. Component preview + security choice → Admins only / All users / Specific profiles
      ▼
 4. Metadata installation              → objects, fields, layouts, labels, tabs, permission sets,
      │                                  CMDT types AND their packaged records
      ▼
 5. Apex installation                  → classes compiled in the subscriber org;
      │                                  packaged tests may be run (esp. production installs)
      ▼
 6. Post-install script (InstallHandler) → your Apex runs, as a special "package ghost" context
      ▼
 7. Licence record created in YOUR PBO via the LMA
      ▼
 8. Admin does post-install config     → assign permission sets, edit CMDT, add the app to profiles
      ▼
 9. Users use the app

Do it

bash
# 1. A clean, customer-like org
sf org create scratch -f config/customer-like-scratch-def.json \
  -a customer1 -d 2 --no-namespace --target-dev-hub devhub

# 2. Install exactly as a customer would (CLI == clicking the URL)
sf package install --package 04t...CORE --installation-key "LearnPackaging123" \
  --target-org customer1 --wait 20 --publish-wait 20 --no-prompt

# 3. Confirm
sf package installed list --target-org customer1
sf org open --target-org customer1
FlagWhat it does
--wait 20Poll the PackageInstallRequest for up to 20 minutes instead of returning immediately
--publish-wait 20Wait for the version to finish becoming available for installation (newly created versions need a moment)
--security-typeAdminsOnly (default) or AllUsers — the profile-access choice from the UI
--upgrade-typeBehaviour for deprecated components on upgrade: DeprecateOnly / Mixed / Delete. Verify before using anything but the default
--no-promptSkip the “this package contains Apex” confirmation — required in CI

The post-install script

An Apex class implementing InstallHandler, nominated on the package (1GP: Package Manager; 2GP: sf package update --package X --apex-post-install-script Y Verify flag name in your CLI version). It runs after components land, and is the right place to seed configuration or migrate data between versions.

apex
global with sharing class OpsPostInstall implements InstallHandler {
    global void onInstall(InstallContext context) {
        if (context.previousVersion() == null) {
            // FIRST install: seed anything the app needs to run.
            seedDefaults();
        } else if (context.previousVersion().compareTo(new Version(1, 1)) < 0) {
            // UPGRADE from anything older than 1.1: run the one-off migration.
            backfillDueDates();
        }
        if (context.isUpgrade() || context.isPush()) {
            // ...
        }
    }
    private void seedDefaults() { /* ... */ }
    private void backfillDueDates() { /* ... */ }
}

Things that bite in post-install scripts: they run as a special system user (often called the “package ghost”) whose behaviour differs from a normal admin; they are subject to governor limits; they must be resilient to any starting state (some customers upgrade from 1.0 to 2.0 directly); and a failure there is a failed install for the customer. Make them idempotent, small, and asynchronous where possible.

The test matrix — run all seven

#TestHowExpected
1Fresh installClean org, install CoreSuccess; components present with opskit__ prefix
2Install without dependencyClean org, install Field Ops firstFail, naming the required 04t. Read that message carefully — it is what your customer will paste to support
3Install with dependencyCore then Field OpsSuccess
4UpgradeInstall 1.0 (released), then 1.1Success; records created under 1.0 still exist with their data
5Failed upgradeAdd a validation rule that existing data violates, or a required field with no default, then upgradeUpgrade fails and rolls back. This is the single most valuable rehearsal on this page
6UninstallSetup → Installed Packages → UninstallSuccess only if nothing depends on it; Salesforce offers to export the data first
7ReinstallInstall again after uninstallingSuccess, but data is not restored unless you import the export file

Test 5 in detail (do not skip it). Ship 1.0. Create a Service Request with a blank Priority__c. Now build 1.1 where Priority__c is required. Upgrade. Watch what happens. Then reason about which customers would have hit it and how you would have found out. This is the class of bug that generates a Sev-1 at 2am.

What uninstall actually does

  • Removes your components from the org.
  • Offers an export of the data stored in your objects (a zip of CSVs, available for a limited time) — the customer's data is theirs.
  • Refuses if another installed package depends on yours.
  • Verify some component types leave residue or block uninstall (e.g. objects referenced by the subscriber's own custom fields, flows, or reports). Test with a subscriber who has built on top of your objects — that is the realistic case.

Upgrades

Build the four versions

VersionChangeWhat it teaches
1.0Initial productThe baseline lineage
1.1Add: Resolution_Notes__c field, a new global method, a new label, a new permission set entryPurely additive upgrades are safe and boring — the goal
1.2Modify: change default SLA in the CMDT record, change a label's text, add a picklist value, tighten a validation ruleWhich of these overwrite subscriber changes, and which do not
2.0Major: a new object Crew__c, a new LWC, a deprecated global method (@Deprecated, not deleted)Big features without breaking anyone
bash
# for each version: edit sfdx-project.json first
#   "versionNumber": "1.1.0.NEXT",
#   "ancestorVersion": "1.0.0.1",
sf package version create --package "Ops Toolkit Core" --code-coverage \
  --installation-key "LearnPackaging123" --wait 30
sf package version promote --package "Ops Toolkit Core@1.1.0-1"
sf package install --package 04t...1_1 --target-org customer1 --wait 20 --no-prompt \
  --installation-key "LearnPackaging123"
git tag -a core-v1.1.0 -m "Ops Toolkit Core 1.1.0" && git push --tags

What can and cannot change — upgrade edition

ChangeAllowedWhat subscribers experience
Add object / field / class / LWC / label / permission set✔Appears after upgrade. New fields are blank on existing records
Add a global method✔Available to their code
Change public Apex internals✔Invisible
Add a picklist value✔Appears. Restricted picklists + subscriber-added values need care Verify
Change a field label / help text✔Updated — unless the subscriber renamed it, in which case their change is generally preserved Verify
Make a field required✔ technicallyDangerous — existing blank data can fail the upgrade or block their edits
Add a validation rule✔Dangerous — can break their integrations immediately
Delete a global method or class✘Version create fails at build time
Rename an object/field API name✘—
Change a field type (e.g. Text → Number)✘ mostly—
Remove a component from the package✔ (you can stop shipping it)The component stays in their org, orphaned and no longer upgraded. This is why you deprecate rather than delete

How each thing behaves on upgrade

ElementUpgrade behaviour
Customer dataNever touched by the upgrade itself. Only your post-install script can modify it — deliberately
Apex classesReplaced wholesale with your new version and recompiled in the subscriber org. If compilation fails against their org, the upgrade fails
Database fieldsNew fields added (blank). Existing fields keep their data. Removed fields are not dropped
Deleted metadataStays behind in the subscriber org as an orphan. Plan deprecation, not deletion
Permission setsYour changes are applied to the packaged permission set. Assignments the admin made are preserved. Access the admin added to their own permission sets stays theirs
ProfilesPackaged profile settings are merged as suggestions on first install only; do not rely on them — ship permission sets
Custom Metadata recordsDepends on protected/managed state and whether the subscriber edited the row. Verify per field; test it explicitly: edit the row as the customer, then upgrade, then look
LayoutsOnce a subscriber has customised a packaged layout, later package changes to that layout typically do not appear for them. New fields must be added by the admin. Documented pattern for many component types: subscriber customisation wins
FlowsPackaged flows are replaced by the new version; subscribers cannot edit them
DependenciesMust be satisfied at the new version's declared level before the upgrade — upgrade the dependency first
LicencesManaged via the LMA; a version upgrade does not change entitlement by itself

Push upgrades

Salesforce lets ISVs push a version to subscriber orgs without the admin clicking anything — used for patches and critical fixes. It is powerful and correspondingly restricted. Verify which versions are eligible (typically patch-level upgrades), how to schedule a push, and what a subscriber can opt out of, in the current ISVforce Guide before ever planning one. Treat a push as a production change to someone else's org — because it is.

Upgrade rehearsal checklist (before every release)

  • Fresh install of the new version into a clean org: passes
  • Upgrade from the previous released version, with realistic data present: passes
  • Upgrade from the oldest supported version (customers skip versions): passes
  • Upgrade with a non-admin user actively using the app afterwards: still works
  • Upgrade in an org where the admin customised your layouts/permission sets/CMDT rows: behaves as documented
  • Dependency versions upgraded first, in order
  • Post-install script tested for: first install, upgrade from N-1, upgrade from N-3
  • Release notes list the 04t, the dependencies, and any manual admin step
