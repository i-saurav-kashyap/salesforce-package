Part 17

Break It On Purpose

Thirty failures, staged on purpose, in the order you will actually meet them. Each one is a small story: the error, what you will wrongly conclude, what is really happening, how to prove it, the fix, and how to make sure it never happens twice.

How to work this page. Read the error, then answer the Think first prompt out loud before you open the solution. Guessing at a Salesforce error costs minutes; reasoning about it costs seconds and teaches you the platform. Error wording varies by CLI and API version — match on the shape of the message, not the exact string. If you just want a lookup table, go to the Error field guide.

The first 60 seconds: triage before theory

Almost every packaging mystery collapses once you answer five questions in order. Do this before you start editing anything.

 1. WHICH ORG did that command actually talk to?
       sf org list --all        → is the default what you assumed?
       (roughly half of all "impossible" errors die right here)
              │
 2. WHICH LAYER failed?
       source → deploy → package build → install → upgrade → runtime
       Each layer has different causes and different logs. Name the layer out loud.
              │
 3. WHAT DOES THE AUTHORITATIVE RECORD SAY?
       The CLI prints a summary. Salesforce stores the truth:
         ScratchOrgInfo.ErrorCode              (scratch org creation)
         Package2VersionCreateRequest.Error    (2GP version build)
         deploy result / PackageInstallRequest (deploy + install)
              │
 4. WHAT DOES THE FAILING ENVIRONMENT LACK that mine has?
       Build env: no seed data, no manual org config, only declared dependencies.
       Customer org: no admin rights, no unpackaged components, other packages present.
              │
 5. CAN I REPRODUCE IT IN A FRESH ORG?
       Yes → it is in your source.  No → the org is the variable.

How to read a Salesforce error

Salesforce errors have a consistent anatomy once you see it. Take this one:

error
Ops_Core_User: In field: field - no CustomField named Service_Request__c.Resolution_Notes__c found
 └────┬─────┘   └──────────────┬──────────────────────────────────────────────────────────────┘
   the component               what it needed and could not find
   that FAILED                 (the thing that is MISSING)

Read it backwards. The component named first is the victim; the thing at the end is the cause. Beginners open the permission set and stare at it; the fix is almost always to supply the missing field. The same shape appears everywhere:

Error code you will seeWhat it really means
INVALID_CROSS_REFERENCE_KEY“You pointed at something that isn't here.” A component references metadata not present in this org/deployment.
FIELD_CUSTOM_VALIDATION_EXCEPTIONA validation rule fired — possibly the subscriber's, not yours. Very common inside packaged DML.
INSUFFICIENT_ACCESS_ON_CROSS_REFERENCE_ENTITYThe user can touch the record but not something it points to (a lookup target, a parent). Permission model, not code.
FIELD_INTEGRITY_EXCEPTIONValue is the wrong shape for the field — picklist value not in the value set, bad ID type.
UNABLE_TO_LOCK_ROWRow-lock contention. Usually your trigger/queueable fighting the subscriber's automation over the same parent record.
MIXED_DML_OPERATIONYou touched setup objects (User, PermissionSetAssignment) and normal objects in one transaction. Split with System.runAs in tests or an async call in production.
UNEXPECTED_TOKEN / Invalid typeApex compile failure. During a package build this nearly always means a missing dependency declaration.
ENTITY_IS_DELETEDYou are working with an ID that no longer exists — frequently a hard-coded ID that only ever existed in your dev org.
REQUEST_LIMIT_EXCEEDED / LIMIT_EXCEEDEDOrg limit, not code bug. Check sf org list limits before you refactor anything.
DUPLICATE_VALUEA unique field or a duplicate developer name — classic on re-running seed scripts.

A · Authentication and the CLI

Cheap to fix, expensive to misdiagnose

Drill 1 — “No authorization information found”

Very commonCost: minutesLayer: local

error
$ sf project deploy start --target-org dev1
Error (1): No authorization information found for dev1.
Think first: the org still exists in Salesforce. So what exactly is missing, and where does it live?
Root cause, investigation, fix

What is missing is local. Authorisation is a refresh token in a file on this laptop. Four things remove it: the alias was never created here; the scratch org expired; the token was revoked (password change, admin revoke, org deleted); or you have two CLIs reading two different config folders.

bash
sf org list --all        # is dev1 listed? Expired? Status "Connected"?
sf org display --target-org dev1
which -a sf sfdx         # two binaries = two auth stores = endless confusion
ls ~/.sfdx ~/.sf 2>/dev/null

Fix: sf org login web --alias dev1, or recreate the scratch org. If sfdx v7 is present, npm uninstall --global sfdx-cli and re-authenticate.

Prevent: one CLI. Scripts that create orgs rather than assume them. JWT in CI so no human token is ever involved.

Deeper knowledge. Salesforce never gives the CLI your password. The web login returns an authorisation code, which the CLI swaps for an access token (short-lived, ~2 hours) and a refresh token (long-lived). Every command silently uses the refresh token to mint a new access token. That is why revoking a session in Setup → Connected Apps kills your CLI instantly, and why an access token pasted into a script stops working the same afternoon.

Drill 2 — The command worked yesterday and hits the wrong org today

Very commonCost: minutes–hoursLayer: local

error
$ sf project deploy start
Deploying to  customer1@example.com    ← you meant dev1, and you just pushed source into your install-test org
Think first: which invisible piece of state decided that?
Solution

Root cause: the default target org. --set-default on a later sf org create scratch silently moved it. Defaults are stored per project in .sf/config.json and globally in ~/.sf/config.json.

bash
sf config list                      # project + global defaults
sf config get target-org target-dev-hub
sf config set target-org dev1       # project-local

Fix: set it explicitly, and re-create the polluted org if you pushed source into a customer-like org (it is no longer a clean install test — it now has unpackaged components).

Prevent: never rely on defaults in anything you commit. Every script and CI step passes --target-org / --target-dev-hub explicitly. Defaults are for interactive typing only.

Drill 3 — JWT login works locally, fails in CI

Common on day one of CICost: hoursLayer: CI

error
Error: We can't authenticate the user. Verify that the user is authorized in the connected app,
or that the certificate is correct.  (invalid_grant / user hasn't approved this consumer)
Think first: JWT has four moving parts. Which one is different between your laptop and the runner?
Solution

The four parts: the Connected App's consumer key, the private key, the username, and the pre-authorisation of that user. Ranked causes:

  1. Newline mangling in the secret. The PEM was pasted into GitHub without its line breaks, so server.key in the runner is not a valid key. This is the number-one cause.
  2. User not pre-authorised: Connected App → Manage → Edit Policies → Permitted Users = Admin approved users are pre-authorized, and the user's profile/permission set is assigned to the app.
  3. Wrong login URL: sandbox users need --instance-url https://test.salesforce.com.
  4. Certificate mismatch: the .crt uploaded to the app is not the pair of the .key in your secret.
bash
# In the runner, prove the key survived transport before blaming Salesforce:
openssl rsa -in server.key -check -noout
head -1 server.key           # must be -----BEGIN RSA PRIVATE KEY----- (or BEGIN PRIVATE KEY)

Prevent: store the PEM base64-encoded and decode in the workflow, or use a secret store that preserves newlines; test the exact same key locally before committing the workflow.

Drill 4 — API version mismatch

OccasionalCost: minutesLayer: deploy

error
Error: INVALID_TYPE: This type of object is not available for this version of the API
Solution

Root cause: sourceApiVersion in sfdx-project.json, or the apiVersion in a -meta.xml, is newer than the org supports (or older than the metadata type requires). Scratch orgs get the newest release first; a customer sandbox on the previous release does not.

bash
grep sourceApiVersion sfdx-project.json
sf org display --target-org dev1 --verbose | grep -i api

Fix: pin sourceApiVersion to a version every target org supports. Prevent: keep one API version across the repo and bump it deliberately, in its own commit, after a release — never mid-feature.

B · Scratch orgs

Where a bad afternoon usually starts

Drill 5 — Dev Hub not enabled (or not the one you think)

Day-one classicCost: minutesLayer: Dev Hub

error
$ sf org create scratch -f config/project-scratch-def.json -a dev1
Error: The org needs to be enabled as a Dev Hub before you can create scratch orgs.
Solution

Two candidate causes, and the test distinguishes them instantly:

bash
sf org list --all                 # which org carries the (D) default-dev-hub marker?
sf data query --target-org devhub --query "SELECT Id FROM ScratchOrgInfo LIMIT 1"

If the query errors with sObject type 'ScratchOrgInfo' is not supported, Dev Hub really is off → Setup → Dev Hub → Enable (irreversible, and also enable Unlocked and Second-Generation Managed Packages while you are there). If the query works, you simply targeted the wrong org.

Deeper knowledge. “Dev Hub” is not a product or an org type — it is a capability flag on an ordinary org that exposes a set of objects (ScratchOrgInfo, Package2, Package2Version…). That is why the SOQL test above is the definitive check: the objects either exist or they do not.

Drill 6 — Scratch org creation fails on a feature name

CommonCost: minutesLayer: Dev Hub

error
Error: The feature 'PersonAccount' is not valid.
Think first: the CLI message is short. Where is the long version stored?
Solution

Root cause: feature names are exact strings that change between releases (here: PersonAccounts, plural). Some features also require a specific edition, or conflict with another feature.

bash
sf data query --target-org devhub --query "SELECT SignupUsername, Status, ErrorCode, Description \
FROM ScratchOrgInfo ORDER BY CreatedDate DESC LIMIT 3"

That ScratchOrgInfo row holds the real, detailed error — always richer than the CLI line.

Prevent: keep definition files minimal. Add one feature at a time and commit each working state, so a broken org definition is always a one-line diff.

Drill 7 — “Maximum number of active scratch orgs”

Blocks whole teamsCost: hours if unmanagedLayer: Dev Hub

error
Error: You have reached the maximum number of active scratch orgs allowed for your Dev Hub.
Solution
bash
sf org list --all                                    # find forgotten aliases
sf org list limits --target-org devhub               # your actual allowance
sf data query --target-org devhub --query "SELECT SignupUsername, ExpirationDate, CreatedBy.Name \
FROM ActiveScratchOrg ORDER BY CreatedDate"          # who is holding the slots
sf org delete scratch --target-org old1 --no-prompt

The subtle version: orgs leaked by failed CI jobs. A job that dies between “create org” and “delete org” holds a slot for its full duration.

Prevent: every CI cleanup step runs with if: always(); short --duration-days; a scheduled sweep that deletes CI orgs older than a day. There are also daily creation limits distinct from active limits — hitting the daily one means waiting, not deleting.

Drill 8 — Source tracking conflict

CommonCost: minutes, or a lost afternoon's workLayer: deploy

error
Error: We found a conflict in the org and your local project:
  Service_Request__c.Priority__c   (Changed in both)
Think first: which copy is authoritative here — and how would you even know?
Solution

Root cause: you changed a field in the org UI and the same file locally. The CLI refuses to pick a winner, which is correct behaviour.

bash
sf project retrieve preview --target-org dev1   # what changed in the org
sf project deploy preview  --target-org dev1    # what would go up, and what conflicts
sf project retrieve start --metadata CustomField:Service_Request__c.Priority__c --target-org dev1
git diff                                        # now SEE the org's change before deciding

Fix: retrieve, inspect the diff, then keep the right side deliberately. --ignore-conflicts silently discards one side — only use it when you already know which.

Prevent: pick one editing surface per component type. Objects/fields in the UI then retrieved; Apex/LWC in the editor then deployed. Mixing both on the same component is what creates conflicts.

C · Metadata deployment

The layer with the most helpful error messages, if you read them backwards

Drill 9 — Missing cross-reference

Very commonCost: minutesLayer: deploy

error
Error: Ops_Core_User: In field: field - no CustomField named
       Service_Request__c.Resolution_Notes__c found
Solution

Root cause: a permission set (the victim) references a field (the cause) that is not in this deployment or in the org — you added the permission entry but not the field file, or you deployed a subset with --source-dir.

bash
ls packages/core/main/default/objects/Service_Request__c/fields/
grep -rl "Resolution_Notes__c" packages/          # who references it
sf project deploy start --target-org dev1         # deploy the WHOLE directory, not a subset

Prevent: deploy whole package directories. Let CI deploy from a clean checkout into a fresh org — that is what catches “it works on my machine because my org already has it”.

Drill 10 — Deploy succeeds locally, fails from a clean checkout

SneakyCost: hoursLayer: source

Think first: what does your working copy contain that Git does not?
Solution

Root cause: an untracked or ignored file. A -meta.xml that was never added, a component excluded by .forceignore, or a file whose name differs in case (macOS is case-insensitive, Linux CI is not — ServiceRequestservice.cls vs ServiceRequestService.cls will bite you exactly once).

bash
git status --ignored | head -40
cat .forceignore
git ls-files packages/core | wc -l ; find packages/core -type f | wc -l   # mismatch = untracked files
git clone <repo> /tmp/clean && cd /tmp/clean && sf project deploy start --target-org fresh

Prevent: the golden rule of 2GP — if it is not in Git, it does not exist. Deploy from a clean clone once a week, or let CI do it on every PR.

Drill 11 — Deployment order / circular reference

OccasionalCost: minutesLayer: deploy

error
Error: ServiceRequestService: Dependent class is invalid and needs recompilation:
       ServiceRequestSelector: line 12, column 9: Invalid type: Service_Request__c
Solution

Root cause: you deployed Apex before the object it references. Salesforce deploys a single request as one transaction and resolves ordering within it — but not across separate deployments.

Fix: one deployment containing everything. Prevent: stop using --source-dir classes/ as a speed hack; deploy the package directory. If a genuine circular reference exists between two Apex classes, that is fine (Apex allows it within one deploy) — but a circular reference between two packages is impossible by design (see Part 11).

Drill 12 — Namespace prefix confusion after deploying to the packaging org

1GP specialityCost: hoursLayer: deploy

error
Error: Invalid field Service_Request__c.Summary__c for SObject opskit__Service_Request__c
Think first: your local files have no prefix. The org's components do. Who is supposed to add it, and where did that break down?
Solution

Root cause: a mismatch between where the namespace is applied. The rules:

SituationLocal sourceWho applies the prefix
1GP: deploying into a namespaced packaging orgunprefixed, and no namespace key in sfdx-project.jsonThe org, on deploy
2GP: deploying into a namespaced scratch orgunprefixed, with a namespace keyThe scratch org (created namespaced because of that key)
Any org: consuming an installed packageyou must write opskit__ yourselfNobody — it is someone else's namespace to you

Fix: match your project file to the model you are in (the course ships two projects — sample-project/ with a namespace, sample-project/1gp/ without — precisely for this reason).

Prevent: never hard-code a prefixed API name in your own package's code. Use static SOQL or Schema describes and let the platform resolve it.

D · Package version build

The build environment knows nothing about your org — that is the whole lesson

Drill 13 — Namespace not linked

Blocks your first packageCost: minutesLayer: Dev Hub

error
$ sf package create --name "Ops Toolkit Core" --package-type Managed --path packages/core
Error: The namespace 'opskit' is not linked to this Dev Hub, or you don't have permission to use it.
Think first: three separate things have to agree. Name them.
Solution

The three: (1) the namespace registered in the DE org, (2) the Namespace Registry link in the Dev Hub, (3) the namespace string in sfdx-project.json — which is case-sensitive and must match character for character.

bash
grep -n namespace sfdx-project.json
sf data query --target-org nsorg --query "SELECT NamespacePrefix FROM Organization"
# Dev Hub UI: App Launcher → Namespace Registries → is it listed, and Active?

Prevent: do the link once on day one, then prove it with a throwaway sf package create before you write any code.

Drill 14 — The test that only fails during the build

#1 cause of failed 2GP buildsCost: hoursLayer: build

error
$ sf package version create --package "Ops Toolkit Core" --code-coverage --wait 30
Error: Package version creation failed:
  ServiceRequestServiceTest.createsRequestWithSlaDueDate: System.QueryException:
  List has no rows for assignment to SObject
Think first: the test is green in your scratch org. Name three things the build environment does not have.
Solution

Root cause: the test depends on something that exists in your org but is not in the package. The build environment contains only your package directory plus declared dependencies: no seed data, no records you created by hand, no manual Setup changes, no other installed packages, no custom settings rows you typed in, and none of your colleagues' components.

bash
sf package version create list --target-dev-hub devhub          # find the 08c
sf package version create report --package-create-request-id 08c... --target-dev-hub devhub

Fix: create every record the test needs inside the test (@TestSetup). If the data is genuinely part of the product (like the Ops_Setting.Default CMDT row), package it.

Prevent: never SeeAllData=true. Before packaging, run your tests in a brand-new scratch org with no seed data — that org is the closest thing you have to the build environment.

Deeper knowledge. This is the same failure as drill 10 and drill 28, wearing different clothes: your environment has invisible state that your artefact does not carry. Once you recognise the pattern, you will diagnose these in seconds for the rest of your career.

Drill 15 — Missing dependency at build time

Common with multi-packageCost: minutesLayer: build

error
$ sf package version create --package "Ops Toolkit Field Ops" --wait 40
Error: Invalid type: ServiceRequestService
       ServiceRequestConsoleController: line 12, column 9
Solution

Root cause: Field Ops references Core's Apex, but no dependency is declared, so Core was never installed into the build environment. It compiles on your laptop only because your dev org contains both.

json
"dependencies": [ { "package": "Ops Toolkit Core", "versionNumber": "1.0.0.LATEST" } ]

And a version of Core must actually exist for LATEST to resolve to.

Prevent: when a class in package B first references a symbol from package A, add the dependency declaration in the same commit — it is part of the change, not follow-up work.

Drill 16 — Cannot promote: coverage

Painful because it is unfixable in placeCost: a rebuildLayer: build

error
$ sf package version promote --package "Ops Toolkit Core@1.0.0-1"
Error: Can't promote this package version because the code coverage is below 75%,
or code coverage was not calculated when the version was created.
Solution

Root cause: coverage is a property of the version, computed once, at create time, and only when you pass --code-coverage. There is no way to add it afterwards.

bash
sf package version list --verbose --target-dev-hub devhub    # see the Code Coverage column
sf apex run test --target-org dev1 --code-coverage --result-format human   # find the weak classes first
sf package version create --package "Ops Toolkit Core" --code-coverage --wait 30

Also worth knowing: a class with 0% coverage can block you even when the overall number looks fine — check per-class coverage, not just the aggregate.

Prevent: put --code-coverage in every version-create command everywhere, forever. It costs build minutes and saves rebuild hours.

Drill 17 — Ancestry error

Appears the moment you have customersCost: hoursLayer: build

error
Error: The ancestor version [1.0.0.1] is not valid, or you removed or changed a
       component that is part of a released version.
Think first: this error has two completely different causes wearing one message. What are they?
Solution

Cause A — the ancestor itself is wrong: the version you named is not released, does not exist, or belongs to another package. Check with sf package version list --released and sf package version displayancestry --package X --verbose.

Cause B — you broke backward compatibility (the useful case). You deleted or changed something that a released version promised to keep: a global method's signature, a global class, a released object or field. The platform is refusing to let you break subscribers.

bash
git diff core-v1.0.0..HEAD -- packages/core/main/default/classes | grep -E '^-.*global'

That one-liner usually finds it: any removed global line is a suspect.

Fix: put the removed member back and mark it @Deprecated instead. Prevent: treat every global as a permanent API. Review any diff that touches one as an API change, not a refactor.

Drill 18 — The build that never returns

Frustrating rather than hardCost: patienceLayer: build

error
$ sf package version create --package "Ops Toolkit Core" --wait 30
Error: Version create timed out.  Run "sf package version create report -i 08cXXXXXXXXXXXXXXX" to check status.
Solution

Not a failure. --wait is a client-side poll timeout; the build continues in Salesforce regardless. Re-run the report until the request reaches Success or Error.

bash
sf package version create report --package-create-request-id 08c... --target-dev-hub devhub

Why builds are slow: the environment must be provisioned, dependencies installed, metadata deployed, Apex compiled and tests run. More dependencies and slower tests mean longer builds — 5–20 minutes is normal; 40+ happens.

Prevent: generous --wait in CI (40–60), and never kill the job assuming the build died. Killing the client does not cancel the build; you will just have an orphan you must look up by its 08c.

E · Installation

Where your assumptions meet someone else's org

Drill 19 — Missing dependency at install

Every multi-package productCost: minutesLayer: install

error
Error: Please install the following required package versions before proceeding:
  Ops Toolkit Core (04tXXXXXXXXXXXXXXX)
Solution

This is correct behaviour, not a bug. Salesforce never auto-installs dependencies — installing software into someone's org without them asking is not something the platform will do on your behalf.

Fix: install the named 04t first, then retry. Prevent: publish the install order in the listing and the README, script it, and in CI install in a loop in dependency order. Customers do not read wikis; they read the error message and then your listing.

Drill 20 — “Package version not available”

Four causes, one messageCost: minutesLayer: install

error
Error: The package version is not available, or you don't have permission to install it.
Solution

Check in this order — cheapest first:

  1. Beta into production. Not allowed, ever. Promote it, or install into a scratch/sandbox/DE org.
  2. Just created. The version needs a moment to become installable → add --publish-wait 20.
  3. Installation key missing or wrong.
  4. Wrong ID — an 05i or 0Ho pasted where a 04t belongs, or an ID from a different Dev Hub.
bash
sf package version list --verbose --target-dev-hub devhub | grep 04t...   # Released column?

Drill 21 — Install fails on edition or features

Rare until it isn'tCost: hoursLayer: install

error
Error: This package can't be installed because your org doesn't have the required feature or edition
       (e.g. Person Accounts, Multi-Currency, Experience Cloud).
Solution

Root cause: your package contains metadata that only exists when a feature is enabled, so it implicitly requires it. You never noticed because your scratch org definition enabled it.

Fix: either declare the requirement honestly in the listing's supported editions, or make the feature optional (split it into a separate package, or make the dependency dynamic).

Prevent: install-test in a scratch org whose definition has no extra features, at the lowest edition you claim to support. Most ISVs test only on Developer edition and discover this in a customer's Professional edition org.

Drill 22 — Install fails on the subscriber's own metadata

The one you cannot reproduceCost: daysLayer: install

error
Error: Installation failed. Apex compile error in subscriber org:
       Invalid field Territory__c for SObject Account
Think first: your Apex compiled perfectly in the build environment. Why would it fail in their org?
Solution

Root cause: packaged Apex is compiled in the subscriber org, and their metadata is part of the compilation context. Your code referenced a field that exists in your dev org (you or a colleague created it manually, or it came from another package) but not in theirs.

bash
grep -rn "Territory__c" packages/                      # find the reference
# then ask: is that field IN my package? if not, why does my code assume it?

Fix: package the field, or make the reference dynamic and defensive (Schema.getGlobalDescribe() / SObjectType.Account.fields.getMap().containsKey(...)) with graceful degradation.

Prevent: a clean-org install test catches this every single time. It is also why standard-object customisations are risky to assume — you do not own Account.

F · Upgrades

Failures here happen in production, in someone else's org

Drill 23 — Upgrade fails on existing data

The 2am escalationCost: days + reputationLayer: upgrade

error
Error: Package upgrade failed.
       Required field is missing: Priority__c on 143 records.
Solution

Root cause: you made an existing field required (or added a validation rule) and the customer's existing data violates it. The upgrade rolls back — which is the good news; the bad news is they are now stuck on the old version.

The correct pattern — a three-version migration:

  1. 1.1 ships the field as not required, plus a post-install script or admin report that populates it.
  2. Customers upgrade and their data becomes clean.
  3. 1.3 makes it required, once the data can satisfy it.

Prevent: the upgrade rehearsal in Part 12 — install the previous released version, seed deliberately messy data (blanks, old picklist values, orphans), then upgrade. Every constraint you tighten is a question about data you cannot see.

Drill 24 — The upgrade “worked” but the customer sees nothing new

Common support ticketCost: hoursLayer: upgrade

Think first: which component types does a subscriber's customisation permanently win over yours?
Solution

Root cause, usually one of three:

  • Layouts. Once a subscriber customises a packaged page layout, your later layout changes typically do not reach them — new fields must be added by their admin. Subscriber customisation wins by design.
  • Permission sets. New components need new permissions; if the admin uses their own cloned permission set instead of yours, your grants never reach their users.
  • Custom Metadata rows. If they edited the row, upgrade behaviour depends on protected/managed state Verify — test it explicitly rather than assuming.

Fix / prevent: ship release notes that state the manual steps in plain language (“add Resolution Notes to your Service Request layout”), and consider a post-install task or an in-app setup page that lists them. Never assume metadata delivery equals user-visible change.

Drill 25 — The post-install script blew up

Hard to debug remotelyCost: daysLayer: upgrade

error
Error: The post install script failed. System.LimitException: Apex CPU time limit exceeded
Solution

Root cause: your InstallHandler did real work synchronously against a customer's data volume. You tested against 20 records; they have 400,000.

Rules for post-install scripts:

  • Idempotent. It may run again; it must not double-create anything.
  • Version-aware. Handle previousVersion() == null (fresh install) and upgrades that skip versions (1.0 → 2.0 directly).
  • Asynchronous for anything data-shaped. Enqueue a Batch/Queueable and let it run outside the install transaction.
  • Fail soft. A caught, logged failure that leaves the app usable beats a failed install.
  • It runs as a special system user whose context differs from an admin's — Verify the current documented limitations before relying on anything exotic there.

Prevent: test the script against a large data set, and test the skip-version upgrade path (1.0 → 2.0), which nobody remembers to test and every customer eventually performs.

G · Runtime in a customer org

“It works for me” is not a diagnosis

Drill 26 — Users see nothing / insufficient privileges

The most common real defectCost: hoursLayer: runtime

Think first: you tested it. What was different about you?
Solution

Root cause, ranked:

  1. You tested as a System Administrator, who has access to everything regardless of your permission set. Your permission set could be empty and it would still “work”.
  2. A component is in your dev org but not in the package.
  3. The permission set is missing classAccesses (LWC dies silently), tabSettings, applicationVisibilities, or field permissions.
  4. Record-level access: your object's OWD is Private and nobody owns the records.
bash
sf org create user --target-org customer1 --set-alias plainuser \
  --definition-file config/plain-user-def.json      # a Standard User, no admin
sf org assign permset --name opskit__Ops_Core_User --target-org customer1 --on-behalf-of plainuser

Then log in as that user and use the app. Make this a release gate — it catches the majority of genuine install defects, and it takes four minutes.

Deeper knowledge. There is a checklist question worth internalising: for every component you add to a package, ask “which permission set grants access to this?” Objects, fields, Apex classes, tabs, apps, record types and page access all need explicit grants. “The admin will do it” is not an answer — the admin does not know what your app needs.

Drill 27 — Works in your org, broken in theirs: namespace

SubtleCost: hoursLayer: runtime

error
System.QueryException: sObject type 'Service_Request__c' is not supported.
Solution

Root cause: a hard-coded API name evaluated in a context that does not resolve to your namespace — typically dynamic SOQL built from a string, a field name in JavaScript, a REST call from outside, or a Flow formula.

Where the name appearsResolves to your namespace?
Static SOQL in your packaged ApexYes — the compiler binds it
Dynamic SOQL inside your packaged ApexUsually yes, via namespace context Inference — test it
A name sent in from LWC/JS, a REST body, or the subscriber's own ApexNo — it needs opskit__
Schema.SObjectType.Service_Request__cYes, and it survives everything — prefer this

Fix: derive names rather than typing them: Service_Request__c.SObjectType.getDescribe().getName() returns the fully-qualified name at runtime, correct in every org.

Prevent: grep your codebase for quoted API names during review. Each one is a question: “where will this string be evaluated?”

Drill 28 — Governor limits that only fire in production

Classic ISV painCost: daysLayer: runtime

error
System.LimitException: Too many SOQL queries: 101
System.LimitException: Apex CPU time limit exceeded
System.DmlException: UNABLE_TO_LOCK_ROW, unable to obtain exclusive access to this record
Solution

Why it only happens there: your code is not alone. In a subscriber org your trigger runs alongside their triggers, their flows, their validation rules, their other vendors' packages, and their data volume. A query inside a loop that is invisible at 10 records is fatal at 10,000.

SymptomUsual causeFix
Too many SOQL queries: 101Query inside a loop, or a trigger that re-entersBulkify; query once into a Map; add a recursion guard
Apex CPU time limitNested loops over large collections; heavy work in a triggerMove to async; reduce algorithmic complexity; process in batches
Too many DML rowsUnbatched updatesCollect and DML once; Batch Apex over 10k+
UNABLE_TO_LOCK_ROWTwo processes updating the same parent (yours + theirs)Reduce lock scope, retry with backoff, avoid updating shared parents in triggers
You have uncommitted work pendingCallout after DML in the same transactionCallout first, or go async (@future(callout=true) / Queueable)
Heap size limitLoading too many records into memoryfor (X x : [SELECT ...]) query-loop form; SOQL LIMIT; streaming

Prevent: test with 10,000 records, not 10. Seed a scratch org with realistic volume before you release anything that touches a trigger. Inference Packaged code gets some governor allocation separate from subscriber code in certain contexts — treat that as a bonus, never as a design assumption.

Failures that are not about code at all

Drill 29 — Git / source drift (the 1GP special)

Silent for monthsCost: weeksLayer: process

Symptom: your released 1GP version contains a field that exists nowhere in Git — or a change you merged three months ago never reached a customer.

Solution

Root cause: in 1GP the packaging org is the source of truth, so any UI change made directly in that org is invisible to Git. Drift accumulates quietly and surfaces during an audit, a migration, or a “why does production have this?” conversation.

bash
sf project retrieve start --manifest package.xml --target-org pkgorg
git status                    # every line here is drift
git diff --stat

Fix: reconcile deliberately, commit the truth, and agree that all future changes are deployed from Git.

Prevent: restrict who can log into the packaging org; run a scheduled retrieve-and-diff that fails loudly; or move to 2GP, where this entire category of bug cannot exist because there is no org to drift from.

Drill 30 — A secret leaked, or CI can suddenly publish

Security incidentCost: whatever it costsLayer: process

Symptom: server.key, an SFDX auth URL, or an access token appears in a commit, a log, or a screenshot.

What to do, in order
  1. Assume it is compromised the moment it is exposed. Rotating later is not equivalent to rotating now; public repos are scraped within minutes.
  2. Revoke: in the org, Setup → Connected Apps OAuth Usage → revoke; delete/regenerate the Connected App certificate; sf org logout everywhere it was used.
  3. Rotate: new key pair, new secret in the CI store, new install keys if those leaked.
  4. Purge: removing a file in a later commit does not remove it from history — rewrite history or treat the credential as permanently burned (usually the latter is faster and safer).
  5. Review what it could do: a Dev Hub credential can create package versions as you. That is a supply-chain risk to every customer, not an inconvenience.

Prevent: .gitignore covering .sf/, .sfdx/, *.key; secret scanning enabled on the repo; workflows that write the key to a file and delete it in the same step; environment protection rules so only the release workflow can read release secrets; and never echo a secret, even “temporarily”.

The method, generalised

  1. Which org? Say it out loud and verify with sf org list --all. This alone resolves a large share of “impossible” errors.
  2. Which layer? Source, deploy, build, install, upgrade, runtime. Same symptom, six different causes.
  3. Read the authoritative record, not the CLI summary. ScratchOrgInfo, Package2VersionCreateRequest, the deploy result, the install request. The CLI truncates; the record does not.
  4. What does the failing environment lack that mine has? This single question solves drills 10, 14, 22 and 26.
  5. Reproduce in a fresh org. Reproducible → it is in your source. Not reproducible → the org is the variable, and now you know which one.
  6. Write the prevention down — a test, a CI step, or a line in the release checklist. A bug you fixed twice was never really diagnosed.
