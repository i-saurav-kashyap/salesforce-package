You cannot learn packaging with a Hello World. Packaging problems only appear when you have an object customers store data in, Apex customers cannot edit, a UI that carries your namespace, permissions you must ship, and configuration customers are allowed to change. So we build that first.

Everything on this page already exists on disk, in sample-project/ next to this site. The code blocks below are read directly from those files, so what you see is what you deploy.

The product: “Ops Toolkit”

A field-operations add-on. A customer's dispatcher raises Service Requests against an Account, the system applies an SLA to compute a due date, and a console lets a field lead see what is open and close it out.

It ships as two 2GP packages plus one 1GP package used purely for the legacy exercise:

What each directory is, precisely

  • packages/<name>/ — a package directory. In 2GP, the boundary of a package is literally “the files under this path”. Move a file between these folders and you have moved it between packages. That is why the folder layout is an architectural decision, not cosmetics.
  • main/default/ — convention inherited from the DX default project. Nothing magic; it keeps room for other bundles (main/test/) later.
  • config/*.json — scratch org definition files. Not packaged. They describe the org you want the Dev Hub to build.
  • scripts/ — not packaged. Your local automation. Everything here should also be runnable by CI.
  • sfdx-project.json — the most important file in a 2GP repo. Package names, versions, dependencies, namespace, and the auto-maintained packageAliases map from friendly names to 0Ho/04t IDs. Always commit it after creating a version.

Business logic — and your first irreversible API decision

[[file sample-project/packages/core/main/default/classes/ServiceRequestService.cls apex]]

Read the global keywords again. In a managed package:

  • public = visible only inside your namespace. You can change it freely forever.
  • global = visible to subscribers and other packages. Once released you can never change its signature, never remove it, and never make it less visible. You can only add.

Beginners mark everything global “to be safe”. That is the opposite of safe: it freezes your internals forever. Mark global only what is genuinely an API.

What the namespace does to this component. In your dev org you use <c-service-request-console>. In a subscriber org, after install, the same component is <opskit-service-request-console>, the label import c.Ops_Request_Created resolves to opskit__Ops_Request_Created, and the Apex import resolves to opskit.ServiceRequestConsoleController. You write c.; the platform rewrites it. This is exactly why you must test in a non-namespaced org with the package installed.

Permission set — the most commonly forgotten component

[[file sample-project/packages/core/main/default/permissionsets/Ops_Core_User.permissionset-meta.xml xml]]

Rule of thumb: for every component you add to a package, ask “which permission set grants access to this?” Object, fields, Apex classes, tabs, apps, and record types all need explicit grants. If your answer is “the admin will do it”, your install experience is broken.

Build and run it (in a scratch org, before any packaging)

[[code bash]] cd sample-project git init && git add -A && git commit -m "feat: ops toolkit application" # create a dev scratch org, push, assign permission sets, seed data, open it ./scripts/create-dev-org.sh dev1 7 # run all tests with coverage - this must be green before you package anything sf apex run test --target-org dev1 --code-coverage --result-format human --wait 10 [[/code]]

Verification for this stage:

  • sf project deploy start completes with no errors
  • All Apex tests pass and org-wide coverage is above 75%
  • You can open the Service Requests tab and create a record; the due date defaults to today + SLA days
  • The validation rule rejects a due date before the requested date
  • The Service Request Console LWC lists open requests on an app page and can complete them
  • Everything is committed to Git

Do not go further until this passes. Every packaging error you meet from here is much easier to diagnose when you know the application itself is sound.
