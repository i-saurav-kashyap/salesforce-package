Part 9

Scratch Org Strategy

Scratch orgs are the reason 2GP development feels different. Understanding them properly removes about half of the confusion beginners have with packaging.

Why scratch orgs exist

Before them, a Salesforce developer's environment was a long-lived org that slowly filled with half-finished experiments nobody dared delete. Two developers on one org overwrote each other. Nobody could answer “is this org the same as production?”

A scratch org inverts that: it is defined by a file, created in minutes, and expected to die. If your org's state matters, it is because your source is incomplete — which is exactly the bug you want surfaced early.

How the Dev Hub creates one

 sf org create scratch -f config/project-scratch-def.json
        │
        ├─► CLI reads the definition file + sfdx-project.json (namespace)
        │
        ├─► CLI inserts a ScratchOrgInfo record into the DEV HUB
        │        Edition, Features, Settings, Namespace, DurationDays, AdminEmail
        │
        ├─► Salesforce org-provisioning service builds a NEW org from a template
        │        applies edition, licences, features and settings
        │
        ├─► ScratchOrgInfo.Status → Active, with LoginUrl / SignupUsername / AuthCode
        │
        └─► CLI authenticates to the new org and saves it under your alias

Documented The ScratchOrgInfo record is the audit trail: you can query it in the Dev Hub to see every scratch org ever requested, who requested it, and why a creation failed.

bash
sf data query --target-org devhub --query "SELECT SignupUsername, Status, ExpirationDate, ErrorCode \
FROM ScratchOrgInfo WHERE Status != 'Deleted' ORDER BY CreatedDate DESC LIMIT 10"

The definition file

sample-project/config/project-scratch-def.json
{
  "orgName": "Ops Toolkit Dev",
  "edition": "Developer",
  "features": ["EnableSetPasswordInApi"],
  "settings": {
    "lightningExperienceSettings": { "enableS1DesktopEnabled": true },
    "mobileSettings": { "enableS1EncryptedStoragePref2": false }
  }
}
KeyMeaningNotes
editionDeveloper, Enterprise, Group, Professional, Partner Developer, Partner Enterprise…Changes which licences and limits exist. Test against the editions your customers use.
featuresOpt-in capabilities: PersonAccounts, Communities, ServiceCloud, API, MultiCurrency, StateAndCountryPicklist…A misspelled feature is a hard creation failure. Verify the current feature list in the DX Developer Guide — it changes every release
settingsMetadata settings applied at creation (Lightning, Chatter, Case settings…)Replaces the old orgPreferences block, which is removed
hasSampleDataSeeds standard sample dataHandy for customer-like orgs
orgName, adminEmail, country, languageCosmetic/localeSet adminEmail to a real address you can receive at

Namespaced vs non-namespaced scratch orgs

NamespacedNon-namespaced
HowDefault when sfdx-project.json has namespace--no-namespace flag
Your components appear asopskit__Service_Request__cService_Request__c
Good forDevelopment — you see prefixes exactly as customers will; namespace-sensitive bugs surface earlyInstall testing — the org has no namespace of its own, so the installed package's prefix behaves exactly as in a real customer org
TrapSome tools/tests written without the prefix silently work here and fail elsewherePushing source here gives you unprefixed components that then collide conceptually with the packaged ones — don't mix

Why a non-namespaced org is the right customer simulation. A real subscriber org has no namespace. When your package installs there, your namespace is added to your components and the subscriber's own components stay unprefixed. A non-namespaced scratch org with your package installed reproduces exactly that arrangement. A namespaced scratch org does not: it makes locally-pushed components look packaged when they are not, which hides the difference between “this works because I pushed it” and “this works because it is in the package”.

Source tracking, push, pull, deploy, retrieve

CommandDirectionWorks withNotes
sf project deploy startlocal → orgAny orgIn a source-tracked org with no flags, deploys only changed files (the modern replacement for force:source:push)
sf project retrieve startorg → localAny orgUse --metadata Flow:My_Flow to grab something you built in the UI
sf project deploy preview—Tracked orgsShows what would deploy — use before every push when unsure
sf project retrieve preview—Tracked orgsShows org changes you have not pulled
sf project reset tracking—Tracked orgsNuclear option when tracking gets confused
sf org delete scratch—ScratchFrees an active-scratch-org slot immediately

Conflicts. If you change a field in the org UI and the same file locally, the CLI stops and reports a conflict. Resolve deliberately: --ignore-conflicts silently discards one side. In a scratch org the local side is almost always the one to keep.

Expiration and limits

  • --duration-days 1–30, default 7. An expired scratch org is gone, not archived.
  • Your Dev Hub has limits on active scratch orgs and daily creations, which vary by edition and partner status. Verify yours:
    bash
    sf org list limits --target-org devhub
sf limits api display --target-org devhub
  • Hitting the daily limit is a common mid-afternoon CI failure. Delete orgs you are done with: sf org delete scratch --target-org dev1 --no-prompt.

A practical lifecycle

Monday morning
  ├─ sf org create scratch -a dev1 -d 7          (namespaced, from project-scratch-def.json)
  ├─ sf project deploy start                     (all source)
  ├─ sf org assign permset ...                   (yourself)
  └─ sf apex run --file scripts/apex/seed-data.apex

During the week
  ├─ edit code → sf project deploy start          (only changes)
  ├─ built something in the UI? → sf project retrieve start --metadata Flow:X
  ├─ sf apex run test --code-coverage             (before every commit)
  └─ commit + push (Git is the truth, the org is not)

Before packaging
  ├─ sf package version create --code-coverage
  ├─ sf org create scratch -a customer1 --no-namespace  (customer-like def)
  ├─ sf package install --package 04t...
  └─ click through the app as a NON-ADMIN user

Friday
  └─ sf org delete scratch --target-org dev1 --no-prompt
     If deleting it makes you nervous, something important is not in Git. Fix that.

Which org for which job

JobOrgWhy
Writing codeNamespaced scratch org, 7 daysFast, disposable, shows prefixes
Reviewing a colleague's PRFresh scratch org from their branchProves the branch is self-contained
CI validationScratch org created and destroyed by the jobNo shared state to corrupt
Install testingNon-namespaced scratch org, Enterprise editionClosest thing to a customer
Upgrade testingNon-namespaced org with the previous released version installedThe only way to test an upgrade path
Demo / UATLong-lived partner test org or 30-day scratch orgNeeds stable data
Reproducing a customer bugTheir sandbox (with permission) or an org matching their edition/featuresEdition and feature differences cause real bugs

Exercise

  1. Create dev1 (namespaced) and customer1 (--no-namespace).
  2. Push source to dev1 only. Install your package's 04t into customer1 only.
  3. In both orgs, open Object Manager and note the API name of the Service Request object. Explain to yourself why dev1 shows opskit__Service_Request__c even though you never typed a prefix.
  4. In customer1, try to edit ServiceRequestService. Note the error. That is namespace isolation.
  5. Delete both. Recreate dev1 from scratch in one command and confirm nothing was lost.
  • I can create either kind of org from memory
  • I can explain why install testing needs a non-namespaced org
  • I know how to see why a scratch org creation failed (ScratchOrgInfo.ErrorCode)
  • Deleting my dev org costs me nothing
