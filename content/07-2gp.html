Start over. Do not carry the 1GP mental model across — it will actively mislead you. 2GP is not “1GP with commands”. It is a different theory of what a package is.

1GP: a package is a list of components living in an org. A version is a snapshot of that org.
2GP: a package is a folder of source in your repo. A version is a build of that source, compiled by Salesforce in a temporary environment it creates and throws away.

The pieces

Dev Hub

The org that owns your 2GP world. It stores:

ObjectHoldsYou query it with
Package2Package definitions (0Ho)sf package list
Package2VersionEvery version built (05i), incl. its 04tsf package version list
Package2VersionCreateRequestEach build attempt (08c) and why it failedsf package version create list/report
ScratchOrgInfoEvery scratch orgsf org list, SOQL

Everything the CLI shows you about packages is a query against these objects in the Dev Hub. That is worth remembering when a command output looks wrong: you can go read the raw record.

Namespace org & the Namespace Registry

Still a DE org, still permanent, still the only place a namespace can be registered. The difference: in 2GP the namespace org is not where you build anything. You register the namespace there once and then link it to the Dev Hub:

  1. In the namespace org: register the namespace (identical to the 1GP steps).
  2. In the Dev Hub: App Launcher → Namespace Registries → Link Namespace → log in as the namespace org's admin → consent.
  3. Verify: the namespace appears in the Namespace Registries list with status Active, and sf package create stops failing with a namespace error.

Unlocked packages (a different 2GP flavour, for a customer's own internal metadata) can be created with no namespace. Managed 2GP for AppExchange always needs one.

Scratch org

Your development environment, created by the Dev Hub from a JSON definition and thrown away. Deep-dive: Part 9. Two facts that matter here:

  • If sfdx-project.json has a namespace, new scratch orgs are namespaced by default — your components get the prefix as you develop, which is what you want while building.
  • --no-namespace gives you a customer-like org — what you want when installing a version.

Package version, beta, promotion

  • sf package version create always produces a beta: installable in scratch/sandbox/DE orgs, not production, and not part of the upgrade lineage.
  • sf package version promote marks it released. That requires ≥75% Apex coverage computed at version create time — which is why you pass --code-coverage when creating any version you might promote. Documented
  • Promotion is irreversible. Verify the current expiry rules for unpromoted versions before relying on an old beta.

Package ancestry — the concept 1GP never needed

Because every 2GP version is built from arbitrary source, Salesforce cannot infer what a new version upgrades from. You declare it:

[[code json]] { "path": "packages/core", "package": "Ops Toolkit Core", "versionName": "Summer Release", "versionNumber": "1.1.0.NEXT", "ancestorVersion": "1.0.0.1", "default": true } [[/code]]

What ancestry buys you:

  • Subscribers on 1.0 can upgrade to 1.1 (no ancestor → no upgrade path).
  • Salesforce can enforce compatibility at build time — if you deleted a released global method, the version create fails instead of the customer's org failing.
  • You can branch: a hotfix line and a feature line can each declare the same ancestor.

Skipping ancestry is the #1 2GP beginner mistake. You ship 1.0, customers install it, then you build 1.1 without ancestorVersion — and discover that customers cannot upgrade, only uninstall/reinstall (losing data). Verify the current options (e.g. --skip-ancestor-check) and their consequences before using them.

Installation & upgrade

Identical mechanics to 1GP from the subscriber's point of view: an 04t, an install URL, an upgrade that preserves data. The customer cannot tell which generation your package is (except by looking at details in Setup). Inference
