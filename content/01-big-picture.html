Every term you will meet, defined once, in the order that makes them build on each other. Read this once now; come back to it whenever a page uses a word you are not sure about.

Group 1 — Orgs (the environments)

Salesforce org

An org (short for organisation) is one isolated tenant of the Salesforce platform: its own data, users, metadata, limits, and URL. Salesforce is multi-tenant — thousands of orgs share the same infrastructure — but no org can see another's data. Every single thing in this course happens inside some org. When you get stuck, the first question is always “which org am I actually talking to?”

Developer Edition (DE) org

A free, permanent, feature-rich but tiny org (limits measured in megabytes and a handful of licences). You sign up at developer.salesforce.com/signup. DE orgs are the only orgs in which you can register a namespace, which makes them the foundation of both packaging generations. Verify Salesforce may deactivate DE orgs after long periods of inactivity — log into your namespace org occasionally.

Partner Business Org (PBO)

The org Salesforce provisions for a company that has joined the Partner Program. It is not a technical necessity for building packages — it is a commercial one. It is where you get:

  • the Partner Console / Publishing Console (create listings, submit Security Review),
  • the Environment Hub (create and track all your other orgs),
  • the License Management App (LMA) (see who installed your package, manage licences),
  • frequently, the Dev Hub for the company's 2GP packages,
  • Trialforce / test-drive org management.

One company normally has exactly one PBO. It must never be deleted.

Dev Hub

Not a separate product — a feature you switch on inside an org (Setup → Dev Hub). Once enabled, that org can:

  • create and track scratch orgs (records in the ScratchOrgInfo object),
  • own 2GP packages (Package2) and package versions (Package2Version),
  • link namespace registries.

2GP cannot exist without a Dev Hub. 1GP does not use one at all. Enabling Dev Hub is irreversible, and the org that hosts it is effectively permanent: it owns your package identity.

Scratch org

A disposable, source-driven org created from a JSON definition file, living 1–30 days (default 7). You describe the org you want (edition, features, settings, optional namespace) and the Dev Hub builds it. Scratch orgs support source tracking: the CLI knows which local files differ from the org, so sf project deploy start / sf project retrieve start move only what changed. Full treatment: Scratch org strategy.

Sandbox

A copy of a production org (metadata, and optionally data), used by customers — and by you, when you test against a realistic environment. Sandboxes belong to the production org that spawned them and refresh from it. As an ISV you mostly do not use sandboxes for development; you use them to reproduce a customer's environment, because a subscriber's sandbox is where they test your upgrade. Documented Beta package versions can be installed in sandboxes and scratch/DE orgs, not in production.

Packaging org 1GP

The single DE org where a 1GP managed package is defined. Its contents are the package. You develop elsewhere and deploy in, or you develop directly in it. If it is lost, your package lineage is effectively lost with it — you cannot recreate the same package elsewhere, because the namespace is stuck in that org. 2GP has no equivalent.

Subscriber / customer org

Any org that installs your package. From your code's point of view it is hostile territory: you do not control its profiles, its other managed packages, its data volume, or its admin. You can only observe it if the customer grants Subscriber Support access, which you reach through the LMA in your PBO.

Trialforce org / template

Trialforce is how AppExchange “Try it free” works. You build a Trialforce Source Org (TSO) that contains your package plus sample data, branding, and users; you snapshot it into a Trialforce Template; Salesforce then spins up a fresh trial org from that template for each prospect. Verify Trialforce provisioning, TSO expiry, and template approval rules change; confirm current steps in the ISVforce Guide before you plan a launch around it.

Group 2 — Identity (the namespace)

Namespace

A 1–15 character globally-unique prefix (letters/numbers, must start with a letter) that Salesforce stamps onto every packaged component: acme__Service_Request__c, acme.ServiceRequestService, acme__Manage_Requests. It gives you:

  • Collision avoidance — your Status__c can coexist with the customer's Status__c.
  • Isolation — subscribers cannot edit your Apex; your code runs in its own namespace context.
  • Identity — the namespace is the brand key of the package forever.

Namespace rules that bite beginners Documented: a namespace is registered in exactly one org; it cannot be changed, transferred, or released; it is globally unique across all of Salesforce; and once a managed package version has been released with it, you live with it. Pick a boring, short, real one (opskit), never test1.

Group 3 — Packages

Package

A container that bundles metadata components for distribution. It is the unit of installation.

Unmanaged package

A one-time bundle of source. On install, everything becomes the subscriber's own metadata: they can edit it, and you can never upgrade it. No namespace, no versioning discipline, no IP protection. Used for templates, samples, and open-source starters — never for a product.

Managed package

A namespaced, upgradeable, IP-protected bundle. Your Apex is hidden from subscribers; you can push upgrades; components are locked from editing unless you deliberately allow it. Requires a registered namespace. This is what you list on AppExchange.

1GP — first-generation managed package

The original (2000s-era) model. The packaging org is the source of truth; you add components to a package in that org's UI and click Upload to mint a version. Automation is limited, branching is painful, dependencies are informal. Still used by large legacy ISVs (Sitetracker's main package is 1GP) because migrating a released 1GP is a big project.

2GP — second-generation managed package

The modern model. Your Git repo is the source of truth. A package is defined in sfdx-project.json; versions are built by a Salesforce-hosted build process from your source; Dev Hub owns the metadata about packages. Supports real branching, CI, explicit dependencies, ancestry, and multiple packages sharing one namespace. Documented Salesforce recommends 2GP for all new managed packages.

Package version

An immutable, numbered snapshot of a package: major.minor.patch.build, e.g. 1.2.0.4. Versions — not packages — are what customers install. You never edit a version; you create a new one.

Beta package version

A version that is not released: testable, and still deletable/replaceable. Documented Beta versions can be installed only in scratch orgs, sandboxes, DE orgs and Trialforce source orgs — not in production/subscriber orgs. A beta is not part of the upgrade lineage: customers can never upgrade from or to a beta. 2GP Every sf package version create produces a beta until you promote it. Verify unpromoted 2GP versions are subject to an expiry window (commonly cited as 30 days) — confirm the current rule before you rely on an old beta.

Released package version

A version marked Managed — Released 1GP or promoted 2GP. It is permanent, installable in production, and part of the upgrade chain. You cannot delete it, un-release it, or change a single byte of it. Everything cautious in this course exists because of this sentence.

Package installation key

An optional password (--installation-key) required to install a version. It stops people who happen to have your 04t from installing your unreleased work. AppExchange-listed packages are normally key-free; internal/beta builds normally have keys. If you don't want one you must say so explicitly: --installation-key-bypass.

Package ancestry 2GP

The declared lineage: “version 1.2 is a descendant of 1.1”. Because 2GP builds each version from whatever is in Git at that moment, Salesforce needs an explicit statement of what the new version is upgrading from in order to (a) enforce that you don't break subscribers, and (b) let subscribers upgrade. You declare it with ancestorVersion / ancestorId in sfdx-project.json. In 1GP, lineage is implicit — the packaging org only ever has one current state, so version N+1 always follows version N.

Package dependency

Package B requires Package A to be present. Declared in sfdx-project.json 2GP, or implied by API references 1GP. Consequences: install order is forced, upgrade order is constrained, and a missing dependency is a hard install failure. Full build-it-yourself treatment: Dependencies.

Group 4 — Distribution

Partner Console (Publishing Console)

The app inside your PBO where the commercial side lives: your Provider profile, your Solutions (a solution = a package version, or an API/bolt-on), your Listings (what shoppers see), your Security Review submissions, and your trial/test-drive configuration.

Security Review

Salesforce's mandatory security assessment before a package can be publicly listed. Automated scanning plus human review of your code, storage of secrets, sharing model, CRUD/FLS enforcement, callouts, and authentication. It is a gate, not a formality: a review failure can cost weeks. Detail and checklist: Security Review readiness.

AppExchange listing

The marketing artefact: title, description, screenshots, pricing, docs, demo video, categories, and the install button that points at your 04t. A listing is not a package. You can have a package with no listing (private distribution by URL) and a listing whose package you update without touching the listing text.

How it all connects — the sentence version

You write metadata on your laptop and store it in Git. You need a namespace, which lives permanently in a Developer Edition org. In 1GP that org is also the packaging org and clicking Upload mints a package version. In 2GP a Dev Hub (usually inside your Partner Business Org) links to that namespace org, creates scratch orgs for you to develop in, and builds package versions from your Git source. Either way you end up with an 04t ID. You install that 04t into a test org, iterate, then release/promote it — making it permanent. You attach the released version to a Solution in Partner Console, pass Security Review, publish an AppExchange listing, and a customer org installs it. When you ship 1.1, the customer upgrades, keeping their data, and your ancestry/lineage is what makes that upgrade legal.
