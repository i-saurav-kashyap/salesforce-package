Your package works. That is roughly half of shipping a product. This page covers the commercial half — and, more importantly, teaches you to keep four things apart in your head that beginners constantly merge into one.

The four things that are not the same thing

What it isWhere it happensCan exist without the others?
Package creationTurning source into a versioned artifact (04t)Dev Hub / packaging orgYes — you can build versions forever and never distribute
Package distributionGetting the 04t into someone's orgAn install URL or sf package installYes — private distribution needs no listing and no Security Review Verify the current rules for private/OEM distribution
AppExchange listingThe marketing page shoppers seePartner Console (Publishing)No — a public listing requires a released version that passed Security Review
Customer installationThe subscriber clicking InstallTheir orgYes — from a URL, with or without a listing

Say it back: “I can build and install a managed package today with zero Salesforce involvement. Security Review and a listing are needed only to sell it publicly on AppExchange.”

Step by step

1. Connect the package to your Partner org

In the Partner Community/Publishing Console you associate your namespace and package with your partner account, and connect it to the License Management App so that installs are recorded and you can manage licences (seats, expiry, suspend/reactivate). Verify the current LMA request and connection steps — this flow has changed several times and is documented in the ISVforce Guide.

What the LMA gives you: a License record per install, the subscriber's org ID and edition, the version they are on, and Subscriber Support login access when they grant it. Without it, you genuinely do not know who is running your software.

2. Create the Solution

A Solution is the technical artefact you are publishing. For a managed package, you choose the package and the released version. This is where your 04t meets the commercial system.

3. Create the Listing

4. Submit for Security Review

Done from the Publishing Console against a specific released version, with your architecture documentation and a review org. See Part 13. Expect a findings report and at least one round trip. Verify current fees, required artefacts and turnaround times.

5. After approval

  • Your listing can be made public; it appears in AppExchange search and category browsing.
  • The listing's install button points at your released version's install URL.
  • You can now be found by customers, and by partners looking for integrations.

6. Managing versions after listing

The listing does not upgrade your customers. Pointing the listing at 2.0 only changes what new installs get. Existing subscribers upgrade when they choose to (or when you push). Communicating upgrades is your job, not AppExchange's.

How customers discover and install

[[diagram]] AppExchange search / category / partner referral / your website ↓ Listing page ──► "Get It Now" ──► log in to their org (prod or sandbox) ↓ Install screen: Admins Only | All Users | Specific Profiles ↓ Dependency check → missing? install order from YOUR documentation ↓ Install → post-install script → admin assigns permission sets → users use it ↓ LMA in your PBO records the licence [[/diagram]]

The moment that decides whether they keep it is the fifteen minutes after install. If an admin installs your package and cannot see anything because they have not assigned a permission set, many will give up. Ship a Getting Started page, a clear README in the listing, and consider a post-install task that points them at the setup steps.

Private and OEM distribution (worth knowing)

  • Private listing / direct URL: distribute the 04t to named customers without a public listing.
  • OEM / embedded: your app is sold with embedded Salesforce licences.
  • Verify which of these still require Security Review and which partner agreements apply — this is contractual, not technical, and you should never advise a customer from memory.

What you should be able to explain

  • The difference between a package, a solution, and a listing
  • Why a package can be installed without ever touching AppExchange
  • What the LMA gives you and where it lives
  • What happens to existing customers when you point the listing at a new version
  • Which parts of this page are process that changes, and where to check the current truth
