Security Review is the gate between “my package works” and “my package is on AppExchange”. It is a real review by real people plus automated scanning, and first-time submissions frequently fail. This page makes you write the vulnerabilities, find them, and fix them.

Verify Submission mechanics, required artefacts, scan tooling versions, fees and turnaround times change regularly. Everything process-related here must be confirmed against the current ISVforce Guide and the Security Review pages in the Partner Community. The technical requirements below are stable.

What Security Review actually is

  • Automated scanning of your package's source (Salesforce Code Analyzer / PMD / Graph Engine and internal tooling), plus scanning of any external web app your package talks to.
  • Human review of the findings, your architecture, how you store secrets, and your documentation.
  • You submit through the Partner Console (Publishing Console), attached to a specific released package version.
  • Failure comes back as a findings report. You fix, produce a new version, and resubmit — which is why you want to be clean before the first submission, not after.

The technical requirements, one by one

1. CRUD and FLS enforcement

The rule: your code must not read or write data the running user is not allowed to read or write — even though your packaged Apex runs in system mode by default.

[[code apex]] // BAD - system mode, no enforcement. Any user with access to your LWC reads everything. public with sharing class Bad { @AuraEnabled(cacheable=true) public static List all() { return [SELECT Id, Summary__c, Priority__c FROM Service_Request__c]; } } // GOOD - the platform enforces object + field permissions for you. public with sharing class Good { @AuraEnabled(cacheable=true) public static List all() { return [SELECT Id, Summary__c, Priority__c FROM Service_Request__c WITH USER_MODE LIMIT 200]; } } [[/code]]
MechanismUse for
WITH USER_MODE on static SOQLThe modern default. Enforces CRUD + FLS + (with sharing) sharing
Database.query(soql, AccessLevel.USER_MODE)Dynamic SOQL
Database.insert(records, true, AccessLevel.USER_MODE)DML
Security.stripInaccessible(AccessType.READABLE, records)Sanitising records before returning them, especially when you must query in system mode for a legitimate reason
Schema.SObjectType.X.isAccessible()/isCreateable()/isUpdateable()/isDeletable()Explicit gate checks before an operation, for clear error messages

If you genuinely need system mode (e.g. writing an audit record the user cannot see), that is allowed — but document why, keep the surface tiny, and expect the reviewer to ask.

2. Sharing

  • Every class declares with sharing, without sharing, or inherited sharing — never leaves it unspecified.
  • Default to with sharing. without sharing needs a written justification.
  • Utility classes called from both contexts should be inherited sharing.
  • Remember: sharing keywords do not enforce FLS or CRUD. They are about records, not fields.

3. SOQL / SOSL injection

[[code apex]] // BAD - user input concatenated into a query. String soql = 'SELECT Id FROM Service_Request__c WHERE Summary__c = \'' + userInput + '\''; // GOOD - bind variable. Nothing to inject into. List rows = [SELECT Id FROM Service_Request__c WHERE Summary__c = :userInput WITH USER_MODE]; // When the STRUCTURE must be dynamic (field names, ORDER BY), use an allow-list. // String.escapeSingleQuotes() protects VALUES only - it does nothing for a field name. private static final Set SORTABLE = new Set{'Name','Status__c','Due_Date__c'}; String field = SORTABLE.contains(input) ? input : 'Due_Date__c'; [[/code]]

4. XSS and the front end

  • LWC escapes bound values by default. The danger is opting out.
  • Never build DOM from strings: no innerHTML, no document.write, no eval, and treat lwc:dom="manual" as a red flag needing justification.
  • In Visualforce: escape="false", JSENCODE/HTMLENCODE misuse, and unescaped merge fields are classic findings.
  • Keep Lightning Locker / Lightning Web Security enabled; do not design around it.
  • Third-party JS must be justified, current, and free of known CVEs. Vendored copies get scanned.

5. Callouts, endpoints and secrets

  • Named Credentials for every callout. No hard-coded endpoints, no credentials in code, custom settings, or CMDT.
  • Remote Site Settings alone are not enough where a Named Credential is possible.
  • Secrets never in: Apex source, static resources, debug logs, custom labels, or a Git repo you submit.
  • If you must store a secret, use Protected Custom Metadata / Protected Custom Settings in a managed package, and explain the model to the reviewer. Verify the currently recommended pattern for ISV secret storage before designing it.
  • Always TLS. Validate certificates. No disabling of security features “for now”.

6. Authentication and authorisation

  • Do not implement your own session handling in Visualforce/Apex.
  • Guest/Experience Cloud access is scrutinised heavily — assume anything a guest user can reach is public to the internet.
  • @AuraEnabled methods are a public API surface for anyone in the org: check permissions inside them, never rely on the UI hiding a button.

7. Test coverage and code quality

  • ≥75% Apex coverage is a hard packaging gate; reviewers also look for meaningful tests (assertions, negative cases, permission tests via System.runAs).
  • @isTest(SeeAllData=true) is a smell. Create your own data.
  • No System.debug of sensitive values.

Scan the app yourself

[[code bash]] # Install the scanner sf plugins install code-analyzer # Scan the whole project sf code-analyzer run --workspace ./packages --view detail # Only the high-severity findings, written to a file you can work through sf code-analyzer run --workspace ./packages --severity-threshold 2 \ --output-file security-findings.html [[/code]]

Verify Code Analyzer's command names and flags differ between v4 and v5 (sf scanner run vs sf code-analyzer run). Run sf code-analyzer --help and use what your installed version supports. Also: a clean local scan does not guarantee a clean Security Review — Salesforce runs additional internal tooling.

Exercise: break it, find it, fix it

Add this class to packages/core, scan, then fix every finding and re-scan.

[[code apex]] // packages/core/main/default/classes/VulnerableDemo.cls // DELIBERATELY INSECURE. Delete before you ever create a package version. public class VulnerableDemo { // 1. no sharing declaration @AuraEnabled public static List search(String term, String sortBy) { String soql = 'SELECT Id, Summary__c, Priority__c FROM Service_Request__c ' + 'WHERE Summary__c LIKE \'%' + term + '%\' ' + // 2. SOQL injection 'ORDER BY ' + sortBy; // 3. injection via ORDER BY return Database.query(soql); // 4. system mode, no FLS } @AuraEnabled public static void wipe(String recordId) { delete [SELECT Id FROM Service_Request__c WHERE Id = :recordId]; // 5. no CRUD check } @AuraEnabled public static String callVendor(String path) { HttpRequest req = new HttpRequest(); req.setEndpoint('https://api.vendor.example.com/' + path); // 6. hard-coded endpoint req.setHeader('Authorization', 'Bearer sk_live_9f3a2b1c'); // 7. secret in source req.setMethod('GET'); System.debug('token used: sk_live_9f3a2b1c'); // 8. secret in logs return new Http().send(req).getBody(); } } [[/code]]
The eight findings and their fixes (try first, then open)
  1. No sharing declaration → public with sharing class VulnerableDemo.
  2. SOQL injection via term → use a bind variable: WHERE Summary__c LIKE :searchPattern with String searchPattern = '%' + term + '%';
  3. Injection via sortBy → allow-list of sortable fields; escaping does not help here.
  4. System-mode query → Database.query(soql, AccessLevel.USER_MODE) or static SOQL with WITH USER_MODE.
  5. Delete without permission check → Database.delete(records, true, AccessLevel.USER_MODE), and check isDeletable() for a clean error message.
  6. Hard-coded endpoint → Named Credential: req.setEndpoint('callout:Ops_Vendor_API/' + path), and validate/whitelist path.
  7. Secret in source → the Named Credential holds the credential; nothing in Apex.
  8. Secret in debug log → delete the line. Never log tokens, even truncated.
[[code bash]] # Prove it sf code-analyzer run --workspace ./packages --view detail rm packages/core/main/default/classes/VulnerableDemo.cls* # do not ship the exercise [[/code]]

Security Review readiness checklist

Code

  • Every Apex class declares a sharing model; without sharing is justified in writing
  • Every SOQL/SOSL enforces user mode, or is explicitly justified
  • Every DML enforces user mode, or is explicitly justified
  • No string-concatenated queries with user input; dynamic structure uses allow-lists
  • Every @AuraEnabled method checks access itself
  • No secrets in source, labels, static resources, CMDT, or logs
  • All callouts go through Named Credentials over TLS
  • No eval, innerHTML, escape="false", or disabled Locker/LWS
  • Third-party libraries are current, licensed, and CVE-free
  • No SeeAllData=true; tests assert behaviour, including negative and permission cases
  • ≥75% coverage overall, with no class at 0%

Package & documentation

  • Permission sets grant exactly what is needed — no over-granting, no Modify All Data
  • The package installs and runs for a non-admin user with only your permission sets
  • A test/review org is prepared with sample data and credentials for the reviewer
  • Architecture/data-flow document: what data leaves Salesforce, where it goes, why
  • External services documented, including their own security posture
  • A local Code Analyzer scan is clean or every remaining finding has a written explanation
  • The released version you intend to submit is the one you tested

Realistic expectation: a first submission that has never been scanned locally almost always comes back with findings. A submission that passes this checklist usually comes back with questions rather than failures. Budget weeks, not days.
