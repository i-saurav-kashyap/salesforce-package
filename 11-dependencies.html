Part 11

Building Package Dependencies

Dependencies are where packaging stops being paperwork and starts being architecture. You will build a three-package chain, then a 1GP→2GP chain, then learn to read the graph.

Part A — A → B → C in 2GP

   Package A — "Ops Toolkit Core"          objects, Apex utility, Custom Metadata
        ▲
        │ depends on
   Package B — "Ops Toolkit Field Ops"     LWC, Apex service, permission set
        ▲
        │ depends on
   Package C — "Ops Toolkit Scheduling"    advanced UI, automation, more Apex

What each package holds and why

A — CoreB — Field OpsC — Scheduling
ContainsService_Request__c, Ops_Setting__mdt + record, ServiceRequestService (global), selector, labels, tab, permission setserviceRequestConsole LWC, ServiceRequestConsoleController, Lightning app, flow, permission setCrew__c, Assignment__c, scheduling LWC, Queueable automation, permission set
Depends on—AB (and therefore A)
Why the splitData model + API everything else builds on. Rarely changes.The everyday UI. Changes often.Premium capability, sold separately, ships on its own cadence.

The real reason to split packages is not tidiness: it is independent release cadence and independent licensing. If Core and Field Ops always ship together and every customer gets both, they should be one package. Every extra package is real overhead — more versions, more install steps, more ways to be out of sync.

Creating package C

bash
mkdir -p packages/scheduling/main/default/{classes,lwc,objects,permissionsets}

sf package create --name "Ops Toolkit Scheduling" --package-type Managed \
  --path packages/scheduling --description "Crew scheduling for Ops Toolkit" \
  --target-dev-hub devhub

FormExampleWhen to use

LATEST vs pinned. LATEST is lovely in development and dangerous in a release build: two builds of B from the same commit can resolve to different versions of A, so the build is not reproducible. Convention that works: LATEST on feature branches, pinned (@1.0.0-3 or a 04t) on release branches.

Why B depends on A — mechanically

ServiceRequestConsoleController (package B) references ServiceRequestService (package A). Apex is compiled when the version is built, so the compiler must be able to see A. The declaration is what makes that happen.

What happens during package version create

sf package version create --package "Ops Toolkit Field Ops"
   │
   ├─ Dev Hub reads sfdx-project.json for this package directory
   ├─ Resolves each dependency to a concrete 04t
   │     "1.0.0.LATEST"  →  newest 1.0.0.x build of Core in this Dev Hub
   ├─ Provisions a temporary BUILD ENVIRONMENT
   ├─ INSTALLS the dependency package versions into it, in order
   ├─ Deploys the source under packages/field-ops
   ├─ Compiles Apex  ← fails here if a dependency is missing or too old
   ├─ Runs tests (with --code-coverage) and records coverage
   └─ Mints Package2Version (05i) + SubscriberPackageVersion (04t),
      recording the resolved dependency list ON the version

Inference The exact provisioning mechanism of the build environment is not publicly detailed; that dependencies are installed into a build environment and that Apex is compiled there is documented behaviour you can observe in the failure messages.

What happens during installation

  1. The subscriber requests install of B's 04t.
  2. Salesforce checks B's recorded dependency list against what is installed in that org.
  3. If A (at a compatible version) is missing, the install fails with a message naming the required package version ID. It does not auto-install it.
  4. If A is present at that version or newer Verify the exact compatibility rule for “newer than declared”, the install proceeds.

Install order — and proving it

bash
# WRONG order, on purpose. Expect failure.
sf package install --package 04t...FIELDOPS --target-org customer1 --wait 20 --no-prompt

# RIGHT order
sf package install --package 04t...CORE     --target-org customer1 --wait 20 --no-prompt
sf package install --package 04t...FIELDOPS --target-org customer1 --wait 20 --no-prompt
sf package install --package 04t...SCHED    --target-org customer1 --wait 20 --no-prompt

sf package installed list --target-org customer1

The failure message is your teacher here: it names the exact 04t the org is missing. Copy it, install that first, retry. Uninstall order is the reverse: you cannot uninstall A while B is installed and referencing it.

When the dependency version changes

ScenarioWhat happensWhat you must do
A ships 1.1 (additive), B still declares 1.0.0.LATESTB keeps building against 1.0.0.x. Subscribers can run A 1.1 with B built on 1.0 — managed packages are backward compatible because global APIs cannot be removedNothing urgent. Bump when B needs A's new API

Part B — Package A = 1GP, Package B = 2GP

Is it supported?

Yes — a 2GP package can depend on a 1GP managed package. Documented This is the normal situation for an ISV that has a large legacy 1GP product and builds new modules as 2GP (exactly Sitetracker's shape: a 1GP core with 2GP feature packages beside it).

The reverse is not available: 1GP has no mechanism at all to declare a dependency. A 1GP package can only reference a 2GP package's components if that package happens to be installed in the packaging org, and nothing will enforce it at the customer's install time. Inference from the absence of any declaration mechanism in 1GP — treat “1GP depends on 2GP” as something to design around, not to rely on.

How the dependency is declared

By subscriber package version ID, because a 1GP package has no entry in your Dev Hub's Package2 table and therefore no alias to name:

json
{
  "path": "packages/field-ops",
  "package": "Ops Toolkit Field Ops",
  "versionNumber": "1.0.0.NEXT",
  "dependencies": [
    { "subscriberPackageVersionId": "04tXXXXXXXXXXXXXXX" }
  ]
}

Optionally give it a friendly name via packageAliases so the file reads better:

json
"packageAliases": {
  "LegacyCore@2.4": "04tXXXXXXXXXXXXXXX"
}

then { "package": "LegacyCore@2.4" }.

Where the 04t comes from

  • Your own 1GP: packaging org → Package Manager → your package → Versions → the version's detail page, or the install URL's p0= parameter, or sf package1 version list.
  • Someone else's 1GP: from their install URL, or from an org that has it installed:
    bash
    sf package installed list --target-org customer1
# or via SOQL in the org that has it installed:
sf data query --target-org customer1 --query "SELECT SubscriberPackage.Name, \
SubscriberPackageVersion.Id, SubscriberPackageVersion.MajorVersion, \
SubscriberPackageVersion.MinorVersion FROM InstalledSubscriberPackage" --use-tooling-api

How it resolves, and what to watch

  1. At version create, Salesforce installs that exact 1GP 04t into the build environment, then compiles your 2GP source against it.
  2. At install, the subscriber org must already have that 1GP package (a compatible version) installed — same rule as any dependency.
  3. At upgrade, the 1GP dependency upgrades on its own schedule; your 2GP module keeps working because the 1GP's global API cannot be removed.

Limitations and cautions

  • A 1GP dependency is pinned to a specific 04t — there is no LATEST resolution for it, so you must edit sfdx-project.json whenever you want to build against a newer 1GP version. That is annoying and also honest: it makes the dependency explicit in your Git history.
  • The 1GP version you depend on should be a released version, not a beta — betas cannot be installed in production, so no subscriber could satisfy the dependency.
  • If the 1GP package needs an installation key, the build environment must be able to install it. Verify the current mechanism for supplying dependency installation keys during sf package version create before you rely on it.
  • Namespace: the 2GP package may live in the same namespace as the 1GP (the migration-friendly shape) or a different one. Verify the current rules and prerequisites for sharing a namespace between a released 1GP package and new 2GP packages — it is supported, and the conditions are specific.
  • Your 2GP code can only call the 1GP's global surface. Anything public in the 1GP is invisible to you, even in the same namespace Verify the same-namespace nuance in your own test before designing around it.

Part C — Thinking in graphs

                 Core Package            ← ROOT: no dependencies, everything needs it
                      │
        ┌─────────────┴─────────────┐
        │                           │
   Feature A                    Feature B     ← both depend on Core, not on each other
        │                           │
        └─────────────┬─────────────┘
                      │
                 Enterprise                   ← LEAF: depends on A and B (and transitively Core)

 INSTALL order:   Core → (A, B in any order) → Enterprise      (topological order)
 UPGRADE order:   same direction — dependencies first, always
 UNINSTALL order: exact reverse — Enterprise → A/B → Core
TermMeaningPractical consequence
Root packageDepends on nothingChanges here are the most expensive — everything downstream rebuilds. Keep it small and stable
Leaf packageNothing depends on itCheapest to change; ideal home for volatile UI
Transitive dependencyEnterprise needs Core through ADeclare direct dependencies; the platform resolves the chain, but you still install the whole chain
Topological orderAn order where every dependency comes before its dependentsThis is your documented install sequence
Circular dependencyA needs B and B needs AImpossible — neither could ever be built first. If you want one, you have one package, not two. Fix by extracting the shared part into a new root package
Dependency conflictTwo packages require incompatible versions of a thirdOnly one version of a package exists per org, so the higher requirement wins; the other package must tolerate it
Version compatibilityDeclared version = minimumManaged packages are backward compatible by construction (no removals), which is what makes this workable

Inspecting the graph with the CLI

bash
# What packages exist in my Dev Hub?
sf package list --target-dev-hub devhub --verbose

# All versions, with released flag and code coverage
sf package version list --target-dev-hub devhub --verbose

# Everything about ONE version, including its resolved dependencies
sf package version report --package "Ops Toolkit Field Ops@1.0.0-1" \
  --target-dev-hub devhub --verbose

# The ancestry tree of a package (which version descends from which)
sf package version displayancestry --package "Ops Toolkit Core" \
  --target-dev-hub devhub --verbose

# What is installed in a given org, and at what version
sf package installed list --target-org customer1

# Raw truth, straight from the Dev Hub objects
sf data query --target-org devhub --use-tooling-api --query \
"SELECT Package2Id, SubscriberPackageVersionId, MajorVersion, MinorVersion, PatchVersion, \
BuildNumber, IsReleased FROM Package2Version ORDER BY CreatedDate DESC LIMIT 20"

Habit worth forming: after every release, run sf package version report --verbose on the version you promoted and paste the dependency list into your release notes. Six months later, when a customer's upgrade fails, that list is the first thing you will want.

Design rules that keep graphs sane

  1. One root, shallow tree. Depth costs install steps and upgrade coordination.
  2. Depend downward only. Never let a stable package reach into a volatile one.
  3. Extract, don't cross-link. The fix for a would-be circular dependency is always a new shared root package.
  4. Pin dependencies on release branches, float them on feature branches.
  5. Document the install order in the listing itself — customers do not read your wiki.
