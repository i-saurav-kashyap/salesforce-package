Part 14

Pipelines for ISV Packaging

2GP exists so that this page is possible. Once Git is the source of truth, releasing is just a job that runs commands — and the discipline that keeps 1GP shops awake at night becomes a YAML file.

The pipeline

    ▼
 Git branch  ──push──►  Pull Request

Authentication in CI — JWT, not passwords

Interactive OAuth cannot work in a runner. The supported answer is the JWT bearer flow: a Connected App in the Dev Hub trusts a certificate you hold.

  1. Generate a key pair (keep server.key out of Git, forever):
    bash
    openssl req -x509 -sha256 -nodes -days 3650 -newkey rsa:2048 \
  -keyout server.key -out server.crt \
  -subj "/CN=OpsToolkitCI"
  2. Create a Connected App in the Dev Hub: Setup → App Manager → New Connected App. Enable OAuth, callback URL http://localhost:1717/OauthRedirect, scopes api, refresh_token offline_access, Use digital signatures → upload server.crt. Save the Consumer Key.
  3. Pre-authorise your user: Manage → Edit Policies → Permitted Users = Admin approved users are pre-authorized, then assign a profile/permission set that includes your CI user.
  4. Test it locally before trusting CI:
    bash
    sf org login jwt --client-id <CONSUMER_KEY> \
  --jwt-key-file server.key --username ci-user@example.com \
  --set-default-dev-hub --alias devhub
  5. Store secrets in GitHub → Settings → Secrets and variables → Actions: DEVHUB_CLIENT_ID, DEVHUB_USERNAME, DEVHUB_JWT_KEY (the whole PEM), PACKAGE_INSTALL_KEY.

Secret hygiene, non-negotiable: the private key never enters the repo; the workflow writes it to a file and deletes it in the same step; secrets are never echoed; use environment protection rules so only the release workflow can read release secrets. A leaked Dev Hub key means someone else can publish package versions under your identity.

Workflow 1 — PR validation

sample-project/.github/workflows/pr-validation.yml
name: PR validation

# Runs on every pull request: static analysis, then a real scratch org where the
# source is deployed and all Apex tests run. Nothing here creates a package version.
on:
  pull_request:
    branches: [main]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install Salesforce CLI
        run: npm install --global @salesforce/cli

      - name: Authenticate Dev Hub (JWT)
        env:
          DEVHUB_CLIENT_ID: ${{ secrets.DEVHUB_CLIENT_ID }}
          DEVHUB_USERNAME: ${{ secrets.DEVHUB_USERNAME }}
          DEVHUB_JWT_KEY: ${{ secrets.DEVHUB_JWT_KEY }}
        run: |
          echo "$DEVHUB_JWT_KEY" > server.key
          sf org login jwt \
            --client-id "$DEVHUB_CLIENT_ID" \
            --jwt-key-file server.key \
            --username "$DEVHUB_USERNAME" \
            --set-default-dev-hub --alias devhub
          rm -f server.key

      - name: Static analysis
        run: |
          sf plugins install code-analyzer
          sf code-analyzer run --workspace ./packages --severity-threshold 2

      - name: Create scratch org
        run: |
          sf org create scratch --definition-file config/project-scratch-def.json \
            --alias ci --duration-days 1 --wait 20 --set-default

      - name: Deploy source
        run: sf project deploy start --target-org ci

      - name: Run Apex tests
        run: |
          sf apex run test --target-org ci --code-coverage --wait 30 \
            --result-format junit --output-dir test-results \
            --test-level RunLocalTests

      - name: Publish test results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: apex-test-results
          path: test-results

      - name: Always delete the scratch org
        if: always()
        run: sf org delete scratch --target-org ci --no-prompt || true
StepTalks toFails when
Install CLInpmRegistry hiccup; pin a version if you need determinism
JWT loginDev HubKey/cert mismatch, user not pre-authorised, wrong username
Code AnalyzerLocal filesA finding above your threshold
Create scratch orgDev HubDaily/active scratch org limit — the most common CI failure
Deploy sourceScratch orgCompile errors, missing dependencies
Apex testsScratch orgFailures or coverage below your bar
Delete scratch orgDev HubRuns with if: always() so a failed job does not leak an org

Workflow 2 — build, install-test, promote

sample-project/.github/workflows/package-release.yml
name: Build and release package versions

# Triggered manually or by a tag. Creates BETA versions, installs them into a clean
# customer-like org, runs the packaged tests there, and (optionally) promotes.
on:
  workflow_dispatch:
    inputs:
      promote:
        description: 'Promote the created versions to released'
        type: boolean
        default: false
  push:
    tags: ['v*']

jobs:
  package:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-node@v4
        with:
          node-version: '20'

      - run: npm install --global @salesforce/cli

      - name: Authenticate Dev Hub (JWT)
        env:
          DEVHUB_CLIENT_ID: ${{ secrets.DEVHUB_CLIENT_ID }}
          DEVHUB_USERNAME: ${{ secrets.DEVHUB_USERNAME }}
          DEVHUB_JWT_KEY: ${{ secrets.DEVHUB_JWT_KEY }}
        run: |
          echo "$DEVHUB_JWT_KEY" > server.key
          sf org login jwt --client-id "$DEVHUB_CLIENT_ID" --jwt-key-file server.key \
            --username "$DEVHUB_USERNAME" --set-default-dev-hub --alias devhub
          rm -f server.key

      - name: Create Core version
        id: core
        run: |
          sf package version create --package "Ops Toolkit Core" \
            --installation-key "${{ secrets.PACKAGE_INSTALL_KEY }}" \
            --code-coverage --wait 60 --json > core.json
          echo "id=$(jq -r '.result.SubscriberPackageVersionId' core.json)" >> "$GITHUB_OUTPUT"

      - name: Create Field Ops version
        id: fieldops
        run: |
          sf package version create --package "Ops Toolkit Field Ops" \
            --installation-key "${{ secrets.PACKAGE_INSTALL_KEY }}" \
            --code-coverage --wait 60 --json > fieldops.json
          echo "id=$(jq -r '.result.SubscriberPackageVersionId' fieldops.json)" >> "$GITHUB_OUTPUT"

      - name: Install into a clean customer-like org
        run: |
          sf org create scratch --definition-file config/customer-like-scratch-def.json \
            --alias installtest --duration-days 1 --no-namespace --wait 20
          for id in ${{ steps.core.outputs.id }} ${{ steps.fieldops.outputs.id }}; do
            sf package install --package "$id" \
              --installation-key "${{ secrets.PACKAGE_INSTALL_KEY }}" \
              --target-org installtest --wait 30 --publish-wait 30 --no-prompt
          done
          sf package installed list --target-org installtest

      - name: Run the packaged tests inside the install-test org
        run: sf apex run test --target-org installtest --wait 30 --result-format human

      - name: Promote (only when asked)
        if: ${{ github.event.inputs.promote == 'true' }}
        run: |
          sf package version promote --package "${{ steps.core.outputs.id }}" --no-prompt
          sf package version promote --package "${{ steps.fieldops.outputs.id }}" --no-prompt

      - name: Commit updated package aliases
        run: |
          git config user.name  "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add sfdx-project.json
          git commit -m "chore: record package version aliases [skip ci]" || echo "nothing to commit"
          git push || true

      - name: Clean up
        if: always()
        run: sf org delete scratch --target-org installtest --no-prompt || true

The install-test step is the point of this workflow. Creating a version proves it compiles. Installing it into a clean non-namespaced org and running the tests there proves it works the way a customer will experience it. Skipping that step is how “it built fine” becomes a support escalation.

Design choices worth copying

  • Promotion is manual and explicit (workflow_dispatch input, or a protected environment requiring approval). Promotion is irreversible — it should never happen by accident on a merge.
  • Beta on every merge, release on a tag. Betas are cheap; use them constantly.
  • The workflow commits sfdx-project.json so the new 04t aliases are recorded in Git. Without this, the repo forgets which commit became which version.
  • Every org is deleted in an always() step. Leaked scratch orgs exhaust your limits and then block everyone.
  • Version numbers are bumped in a PR, not by CI. Deciding “this is 1.1 not 1.0.1” is a human decision about compatibility.

Branch and version strategy

BranchBuildsDependenciesAncestry
feature/*Nothing (PR validation only)LATEST—
mainBeta on mergeLATESTAncestor = last released
release/1.1Beta → approved → promotePinnedAncestor = 1.0.x
hotfix/1.0.1Patch versionPinned to what 1.0 usedAncestor = 1.0.0

Tag every promoted version: git tag -a core-v1.1.0 -m "04t...". The tag message containing the 04t has saved more incidents than any dashboard.

What to add next (in order of value)

  1. Jest tests for LWC (npm run test:unit) in the PR job — fast and catches real bugs.
  2. Prettier + ESLint as a pre-commit hook, so formatting never appears in review diffs.
  3. An upgrade-test job: create an org, install the previous released version, seed data, install the new version, assert the data survived. This is the highest-value job in an ISV pipeline and almost nobody has it.
  4. Scheduled dependency check: nightly job that reports if a dependency has a newer released version.
  5. Release notes generation from the commit range between tags.

Verification

  • JWT login works locally with the same key CI will use
  • A PR triggers validation and it goes green
  • A deliberately failing test blocks the PR
  • The release workflow produces a 04t and installs it into a clean org
  • Scratch orgs are always deleted, even when the job fails
  • Promotion requires a human action
  • The repo contains the alias for every version you have built
