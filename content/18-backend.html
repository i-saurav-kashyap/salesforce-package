What is actually happening when you type a command. Everything here is marked: Documented behaviour Salesforce publishes, Inference a reasonable conclusion from observable behaviour, or Verify something Salesforce does not expose. Nothing is presented as internal knowledge I do not have.

Layer 0 — what the CLI actually is

Documented The sf CLI is a Node.js application built on oclif. It holds no Salesforce logic of its own: it authenticates, calls documented Salesforce APIs, and formats the responses.

APIUsed for
Metadata API (SOAP)deploy / retrieve of metadata as a zip
Tooling API (REST)Packaging objects (Package2, Package2Version, Package2VersionCreateRequest, PackageUploadRequest, PackageInstallRequest), ScratchOrgInfo, anonymous Apex, test runs
REST/SOAP data APIssf data query, record CRUD
OAuth 2.0web flow, device flow, JWT bearer flow

Prove it yourself — the CLI will show you the API traffic:

[[code bash]] SF_LOG_LEVEL=debug sf package version list --target-dev-hub devhub sf package version list --json | jq '.result[0]' # the raw record shape [[/code]]

Layer 1 — authentication

[[diagram]] sf org login web │ ├─ CLI starts a local listener on 127.0.0.1:1717 ├─ opens the browser to /services/oauth2/authorize ├─ you log in + consent (password never touches the CLI) ├─ Salesforce redirects to localhost with an auth code ├─ CLI exchanges the code for access + refresh tokens └─ stores them under ~/.sfdx/.json (mode 600) every later command: refresh token ──► access token ──► API call [[/diagram]]

Documented standard OAuth. Inference the local-listener detail is observable but not contractual; use sf org login device when a browser redirect to localhost is impossible.

Layer 2 — scratch org creation

[[diagram]] sf org create scratch -f config/project-scratch-def.json │ 1. CLI merges: definition file + sfdx-project.json namespace + flags 2. CLI INSERTS a ScratchOrgInfo record into the DEV HUB [Documented] Edition, Features, Settings, Namespace, DurationDays, AdminEmail... 3. Salesforce's org-provisioning service picks it up [Inference] - allocates an org on an instance - applies edition, licences, features, settings - (Salesforce does not publish how this is implemented) [Not exposed] 4. ScratchOrgInfo.Status → Active, with SignupUsername + AuthCode 5. CLI authenticates to the new org and saves the alias locally [[/diagram]]

The useful consequence: when creation fails, the authoritative error is on the ScratchOrgInfo record in the Dev Hub, not in the CLI output.

Layer 3 — metadata deploy

[[diagram]] sf project deploy start │ 1. Resolve source files → metadata components (package.xml built for you) 2. Zip them 3. Metadata API deploy() → returns an async job id 4. CLI polls deployResult until Succeeded / Failed 5. In source-tracked orgs the CLI first asks the org which components changed, so a deploy with no flags sends only the delta. Documented

Layer 4 — 2GP package version creation

This is the one you asked to see in depth.

[[diagram]] sf package version create --package "Ops Toolkit Field Ops" --code-coverage │ [Documented] 1. CLI reads sfdx-project.json: path, version, dependencies, ancestry [Documented] 2. CLI packages the source under that path and uploads it as a VersionInfo blob, then INSERTS a Package2VersionCreateRequest (08c) into the Dev Hub via the Tooling API [Documented] 3. The request enters a queue; status: Queued → InProgress → Success/Error [Inference] 4. Salesforce provisions a BUILD ENVIRONMENT (an org-like environment with your namespace applied). Its exact nature is not published. [Documented] 5. Declared DEPENDENCIES are installed into that environment first (observable: dependency errors surface here as install failures) [Documented] 6. Your metadata is deployed into it [Documented] 7. Apex is COMPILED — unresolved symbols fail the build here [Documented] 8. If --code-coverage: your Apex TESTS run; coverage is recorded ON the version [Documented] 9. Ancestry is validated: removing/changing released global API fails the build [Documented]10. A Package2Version (05i) is created with a SubscriberPackageVersionId (04t) [Inference] 11. The build environment is discarded [Documented]12. CLI writes the new alias into sfdx-project.json [[/diagram]]

Things Salesforce does not publicly expose Verify: how build environments are pooled or scheduled, why the same build takes 4 minutes one day and 25 the next, where the compiled artefact is stored, and how the artefact is distributed to instances at install time. Do not build a process that assumes any of it.

Practical consequences of the pipeline above:

  • Anything your code needs that is neither in the package directory nor in a declared dependency does not exist during the build. That is drills 7 and 8 in Part 17.
  • Your tests run in a place with no seed data and no org customisation. Tests that depend on either will fail there and nowhere else.
  • Coverage is a property of the version, computed once. That is why you cannot promote a version that was created without --code-coverage.
  • Build time scales with dependencies, metadata volume and test duration — not with your patience.

Layer 4b — 1GP version upload, for contrast

[[diagram]] Upload (UI) or sf package1 version create │ [Documented] 1. A PackageUploadRequest record is created in the PACKAGING ORG [Documented] 2. Salesforce reads the package's component list IN THAT ORG [Documented] 3. Validates the component set and its dependencies [Documented] 4. Compiles Apex; for a Managed-Released upload, runs all tests and enforces ≥75% coverage [Inference] 5. Snapshots the components into a distributable artifact [Documented] 6. Mints a SubscriberPackageVersion (04t) + install URL, emails you [[/diagram]]

The structural difference in one line: 2GP's input is your source tree; 1GP's input is the current state of an org.

Layer 5 — installation in a subscriber org

[[diagram]] sf package install --package 04t... (or the install URL) │ [Documented] 1. A PackageInstallRequest is created in the TARGET org [Documented] 2. Validation: is the version released (for production)? key correct? edition/features sufficient? dependencies present? [Documented] 3. Components are created in the org under YOUR namespace [Documented] 4. Apex is compiled IN THE SUBSCRIBER ORG → a compile failure against their org fails the install [Documented] 5. Packaged tests may be run (notably for production installs) [Documented] 6. Your InstallHandler (post-install script) executes [Documented] 7. Licence record created via the LMA in your PBO [Documented] 8. Install request → Success; components visible in Setup [[/diagram]]

Inference Step 4 is why an upgrade can fail in one customer org and succeed in another: their org's metadata is part of the compilation context.

How to verify any claim on this page yourself

[[code bash]] # The packaging objects, straight from the Dev Hub sf data query --target-org devhub --use-tooling-api --query \ "SELECT Id, Name, NamespacePrefix, ContainerOptions FROM Package2" sf data query --target-org devhub --use-tooling-api --query \ "SELECT Id, Status, Package2Id, Package2VersionId, Error FROM Package2VersionCreateRequest \ ORDER BY CreatedDate DESC LIMIT 5" sf data query --target-org devhub --use-tooling-api --query \ "SELECT Id, MajorVersion, MinorVersion, PatchVersion, BuildNumber, IsReleased, \ CodeCoverage, SubscriberPackageVersionId FROM Package2Version ORDER BY CreatedDate DESC LIMIT 10" # What a target org thinks is installed sf data query --target-org customer1 --use-tooling-api --query \ "SELECT SubscriberPackage.Name, SubscriberPackageVersion.Id, \ SubscriberPackageVersion.MajorVersion, SubscriberPackageVersion.MinorVersion \ FROM InstalledSubscriberPackage" [[/code]]

Being able to read these objects directly is what separates “the CLI said something confusing” from “here is exactly what Salesforce recorded and why”. Learn these four queries.
